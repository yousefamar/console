## Architecture
- **PWA** — installable standalone, works in any browser including mobile
- **Android APK** (`android/`) — fully-native Kotlin + Jetpack Compose app, boundary at the hub API, offline-first (Room + outbox + WorkManager; WhatsApp model), optional Android launcher. **Everything mobile-specific lives in `android/CLAUDE.md`** (architecture map, release workflow, live-device debugging via `?target=apk`, the bug classes that have bitten us) — it is auto-loaded when you touch `android/`, so no cwd change is needed and one session can land a hub+APK change together. Cross-cutting rules for hub/SPA work: (1) **APK changes batch, hub/SPA changes deploy immediately** — an APK release is cut only when Yousef says "ship"/"release"; (2) **every new agent-protocol message, hub route or `SessionInfo` field needs an APK twin** (`android/.../data/agents/AgentsRepository.kt` for agents, the matching `data/<domain>/` repo otherwise) — file it in `android/BACKLOG.md` "Open" if you don't build it; (3) keep ephemeral broadcasts (`session_todos`, `boards` events) idempotent and stamp `absIndex` on logged agent messages BEFORE broadcasting (the APK upserts by index).
- **Public SPA + public hub via Caddy.** `con.amar.io` resolves to the home WAN IP (Namecheap DDNS — see Al's `ddns-update.md` workflow), Caddy on :443 with a Let's Encrypt cert serves: `/hub/*` → `https://127.0.0.1:9877` (Caddy strips `/hub`, sets `X-Forwarded-Host/Proto/-Prefix`); `/public/*` → `https://127.0.0.1:9877` (prefix preserved, never auth-gated); legacy `/cron.ics` rewrites to `/public/cron.ics`; legacy `/apk/*` rewrites to `/public/apk/*` (for stuck pre-v21 installs); catch-all → `http://127.0.0.1:5173` (Vite). Hub binds `127.0.0.1:9877` — Caddy is the only external ingress; emergency override is `--host 0.0.0.0`. The global Caddy block forces `protocols h1` on `:443` because HTTP/2 → HTTP/1.1 WebSocket bridging was unreliable for fresh upgrades (chrome timed out on new wss opens). **The hub sets `keepAliveTimeout = 75s` / `headersTimeout = 76s`** (`index.ts`): it must outlive Caddy's idle window so Caddy always closes first, and headersTimeout must exceed keepAliveTimeout or Node kills the next request on a reused socket. SPA's `getHubUrl()` returns `${window.location.origin}/hub`. **Different origin = different IndexedDB** — one-time cross-origin migration UI in `AccountModal` ("Import from another origin"), powered by `src/migration.ts` (hidden iframe + postMessage pump). See `memory/project_public_funnel_arch.md` and `memory/reference_caddy_funnel_setup.md`.
- **Hub auth — cookie + bearer.** Single allow-list (`hubAllowedEmails` in `~/.config/console/auth.json`, default `['yousefamar@gmail.com']`). Browser path: SPA hits `${origin}/hub/auth/google/start?return=…`, hub does Google OAuth, callback sets `console_session=<id>; HttpOnly; Secure; SameSite=Lax; Path=/hub`. Sessions stored in `auth.json` `hubSessions[]`, 30-day TTL. **APK Custom Tab → WebView cookie handoff** via one-time token: hub callback redirects to `console://auth/done?ott=<ott>`; the APK navigates the WebView to `/hub/auth/claim?ott=…` which validates the OTT (single-use, 2-min TTL) and issues a fresh `Set-Cookie` in the WebView's jar. Non-browser path: named bearer tokens (`hubTokens[]`, hashed sha256, individually revocable) sent as `Authorization: Bearer <…>`. Scopes: `cli`, `al`, `apk`, `ring`, `voice`, `other`. CLI + Al read plaintext from `~/.config/console/local-tokens.json` (mode 0600) — auto-minted on hub first boot, separate per scope. APK gets paired via SPA "Pair this APK" → `POST /hub/auth/tokens` → `window.ConsoleNative.setHubToken(…)` → `HubTokenStore.kt` (EncryptedSharedPreferences). PushService attaches the bearer via OkHttp `Request.Builder().header("Authorization", …)` and posts a "needs re-pair" notification on close-4401/4403 or HTTP 401/403 during handshake. **Enforcement** gated by `CONSOLE_AUTH_ENABLED=1`; **break-glass** is `CONSOLE_AUTH_DISABLED=1` (forces allow even if enabled). Both env vars set in pm2's environment. The loopback bypass requires NO `X-Forwarded-*` headers (so Caddy-proxied requests aren't silently treated as same-host). Mutating session-authed requests also pass a `SameSite=Lax`-belt-and-braces `Origin`/`Referer` check (`isCsrfSafe`). Confused-deputy guard: requests carrying BOTH cookie and bearer are rejected. **Pre-auth render gate**: `src/GatedBoot.tsx` is the SPA's only entry point — it probes `/hub/auth/session` first and renders LITERALLY nothing until authenticated; the rest of the app (`App`, sync-bus, stores, panes) is lazy-imported behind the gate so an unauthenticated visitor can't even see pane scaffolding via DOM inspection.
- **Public canvas surface — NO tokens (Yousef's rule).** Each tab/island can be flipped public via `con dashboard canvas {tab,} publish <slug>` (or the Share button on the Home canvas card → `src/components/home/CanvasShareMenu.tsx`) → adds the slug to `~/.config/console/canvas-public.json` (`CanvasPublicRegistry` in `server/src/canvas-public.ts`; sibling of `canvas/` so `con dashboard canvas reset` does NOT silently unpublish — only explicit `unpublish` does). Public URL is the plain slug: `https://con.amar.io/public/<slug>/` (short form, tab-first-then-island; `/public/canvas/<tab|island>/<slug>/` is the explicit fallback for a slug published as both kinds; `canvas`/`apk`/`cron.ics` are reserved slugs) — publish means public, unpublish 404s it. Routes in `server/src/routes/public.ts`: trailing-slash 301, asset path-traversal guard (`path.resolve` ⊂ `tabsDir/<slug>/`), `no-store`/`nosniff`/`no-referrer` HTML headers. Islands are inline-HTML only (no asset paths); tabs serve files from their dir.
- **Unpublished canvas is auth-gated — `/canvas/*` is NOT in the auth exemption list.** `GET /canvas/*` requires a principal; besides session/bearer/loopback, a dedicated read-only cookie `console_canvas` (`HttpOnly; SameSite=None; Secure; Path=/hub/canvas`, value = the hub-session id) authenticates it. Why a second cookie: the SPA canvas iframe is `sandbox="allow-scripts"` (opaque origin), and a TAB canvas's nested tab-frames fetch relative assets FROM that opaque origin — cross-site, so the `SameSite=Lax` session cookie is withheld there; `SameSite=None` is sent. Minted beside the session cookie at the OAuth callback + `/auth/claim`, refreshed on every `GET /auth/session` probe (GatedBoot hits it each load, so existing logins gain it without re-login), cleared on logout. GET-only + path-scoped, so no CSRF surface. Published `/public/canvas/<kind>/<slug>/` shares are a separate always-open path, unaffected. The native APK's Home canvas WebView holds no cookies — it attaches the apk bearer per-request via `shouldInterceptRequest` (HomeScreen.kt). Tests: `server/src/__tests__/canvas-auth.test.ts`.
- **Offline-first** — all mutations (email, chat, calendar) write to IndexedDB first, sync via queue
- **Hub server** — Node.js backend (`server/`) proxies all API calls (Gmail, Calendar, Matrix, Monzo), manages OAuth tokens, hosts agent sessions. Internal HTTPS via any `*.crt`/`*.key` pair in `~/.config/console/` (Caddy terminates the public TLS in front). Binds `127.0.0.1:9877` — all external traffic goes through Caddy.
- **Sub-app isolation** — Layout subscribes only to `activePane`. Each tab component is `React.memo`'d. A chat state change never re-renders the email pane.
- **Pre-rendered panes** — all panes mounted with `display:none`, toggled on selection. `EmailFrame` renders a height-preserving placeholder when `!visible` — live hidden email iframe documents fire recurring ~500 ms browser-internal long tasks that lag typing in OTHER panes (`memory/project_emailframe_iframe_perf.md`).
- **Hub WS heartbeat** — `src/sync-bus.ts` runs a 15 s ping (server already responds at `server/src/sync-bus.ts:95`). 30 s without inbound traffic → `forceReconnect()`. Catches the APK / mobile-Safari "WS half-dead while backgrounded" bug at the source — no visibility-event dependence. See `memory/project_apk_ws_heartbeat.md`.

## Debugging (PRIMARY METHOD)

**Use the embedded debug agent, NOT browser DevTools or Chrome MCP tools.**

The app has a built-in debug agent (`src/debug-agent.ts`) that streams all console output, network requests, and errors to the hub in real-time. Claude Code observes via HTTP endpoints:

```bash
# See recent events (console logs, network requests, errors)
curl -sk https://localhost:9877/debug/log?n=30

# Filter for errors
curl -sk https://localhost:9877/debug/log?n=100 | jq '.[] | select(.cat=="error")'

# Filter for failed network requests
curl -sk https://localhost:9877/debug/log?n=100 | jq '.[] | select(.cat=="net" and .status >= 400)'

# Execute JS in the browser (replaces Chrome MCP javascript_tool)
# ALWAYS pass ?target=chrome — with the APK also connected, an untargeted eval
# can hit its native debug agent, which errors "unknown command" on any JS
# (looks like a syntax problem, is a routing problem).
curl -sk -X POST 'https://localhost:9877/debug/eval?target=chrome' -H 'Content-Type: application/json' -d '{"code":"document.title"}'

# Get Zustand store state
curl -sk https://localhost:9877/debug/state

# Check if debug agent is connected
curl -sk https://localhost:9877/debug/status
```

The debug agent:
- Captures from page load (imported first in `main.tsx`)
- Survives navigation (WebSocket auto-reconnects)
- Works across all tabs/devices (all stream to same hub)
- Logs to `~/.config/console/debug.log` (NDJSON, auto-rotated at 5K lines)
- `window.__console` (dev-only) exposes Zustand stores + Dexie db for browser console access
- **Eval-probe trap**: `import('/src/store/x.ts')` from `/debug/eval` can resolve a DIFFERENT module instance than the app's after HMR churn (empty-looking stores that aren't). Probe via `window.__console.stores` or the DOM, never a fresh dynamic import
- **Isolated SPA verification from a worktree (never Yousef's live tab)**: `npx vite --config vite.verify.config.ts --port 5174` + Playwright against the live hub. The full recipe and every known gotcha (auth-probe shim, setState injection, lazy panes, recurring writers, headless dictation, screenshots) is the **`verify-spa` skill** (`/verify-spa`, user-invocable) — load it before live-verifying UI.

## Key Patterns

### SPA reads a new hub field → optional-guard it, always
Vite HMR ships the SPA reader immediately; the hub writer only ships at the next restart. In that window the live hub serves payloads WITHOUT the new field, and an unguarded access (`d.tags.includes(…)`) crashes the whole React tree, not just one component ("screen goes dark"). Rule: any new field on a hub payload consumed by the SPA gets `?? []` / `?.` at the point of use, no exceptions.

### Prefs: a FAILED load must never look like a loaded one
`src/prefs.ts` is the hub-backed pref cache (`GET/PUT /config`); `isPrefsLoaded()` is the guard every automatic writer uses to avoid persisting a default over the user's real value. `initPrefs()` resolves only on a SUCCESSFUL load, retries with backoff (2/5/15/30/60 s), leaves `isPrefsLoaded()` false until one lands, and grafts newer local writes over a late-arriving hub copy (`localWrites`, the `auth-store` graft lesson). `prefsReady()` therefore never resolves while the hub is unreachable — callers race their own timeout and must not write on that path. Symptom of a regression: *"my settings keep resetting, and then the WRONG ones persist"* — for ANY pref.
- **Corollary for any pref derived from in-memory state**: a Zustand store is created at import time, BEFORE the pref cache is populated (App hydrates it a few ticks later), so a write derived from the store's own state in that window persists a set missing everything. `registerOverlaySource` seeds from `persisted ∪ in-memory` so a register can only ever ADD. **But never DECIDE against an unloaded cache** (^tame-ibis, 2026-09-08): with prefs pending, an empty `overlaySeen` made every overlay look first-seen, the store added it to the in-memory set, and App hydration + `fetchCalendars` unioned that guess over the saved pref — a hidden Meetup came back on every slow boot/restart. Overlay visibility is now settled only after `prefsReady()` (`settleOverlayVisibility`), hydration replaces with `saved ∪ first-seen`, and no path unions the in-memory set over the saved one.

### Auth
- **Hub-managed OAuth** — all tokens stored server-side in `~/.config/console/auth.json`. Frontend bootstraps via `GET /auth/token`. Sign-in opens hub's `/auth/google/start` in a popup.
- **Multi-account** — hub stores multiple Google accounts. Calendar sidebar can add accounts via OAuth flow. **Adding an ADDITIONAL account must pass `?add=1`** to `/auth/google/start` — that switches `prompt` from `consent` to `select_account consent`. Without it Google silently re-consents whichever account the browser is already signed into, so "Add calendar account" just re-links the existing account and the new one never appears. The plain sign-in path deliberately stays `consent` (no chooser).
- **Token refresh** — hub proactively refreshes tokens 5min before expiry. Frontend re-fetches from hub on 401.

### Offline Sync Queue
- **Shared queue** — `src/db/sync-queue.ts` provides `enqueue()`, `markDone()`, `markFailed()` for all services
- **Action types** — email (`archive`, `send`, etc.), chat (`chatSend`, `chatMarkRead`), calendar (`calCreate`, `calUpdate`, `calDelete`, `calRsvp`, `calReminder`, `calLocation`)
- **Pattern** — optimistic IDB write → `set()` for instant UI → `enqueue()` → background processor flushes within 500ms
- **Retry** — 3 retries before marking `failed`. Queue survives page reload.
- **Undo** — delete actions show 5-second undo toast. Undo removes from queue + restores IDB.

### Email
- Optimistic archive/snooze with undo. Auto-archive on reply. Pre-rendered iframes. CID inline images.
- Snooze is local-only (Gmail has no snooze API). Conflict detection before sending queued replies.
- Send-as aliases fetched during sync. Calendar invites parsed from `text/calendar`.

### Chat (Matrix)
- **Hub-owned room snapshot.** The canonical view of every joined room (name, isUnread, unreadCount, avatar, memberCount, tags, snoozedUntil, lastMessage*) lives server-side in `server/src/matrix/chat-rooms-store.ts` (a `SnapshotStore` wrapper from `server/src/snapshot-store.ts`). Every `/sync` delta computes the row via `server/src/matrix/room-state.ts` (port of the SPA's old `processJoinedRoom` logic) and the store broadcasts on the `chat-rooms` service. Browser-side `src/matrix/chat-rooms-subscribe.ts` mirrors snapshot + deltas straight into `db.chatRooms`. Replaces per-device derivation — "mark read on PC → phone sees it" works without local divergence. RPCs registered under `chat-rooms`: `snapshot`, `markRead`, `markUnread`, `snooze`. **Manual unread is durable** (`RoomState.manualUnread`): "mark unread" has no homeserver concept, so the sticky flag forces `isUnread` true across recomputes and is cleared only by an explicit `markRead` (`setRoomRead`) — never by a sync reporting `notification_count=0` (a post-restart catch-up sync touches enough rooms to wipe every marker otherwise).
- Direct REST API (no matrix-js-sdk). E2EE via OlmMachine WASM. Long-polling sync.
- Local echo with `~timestamp.random` IDs. Bridge detection (WhatsApp, LinkedIn, Slack).
- Pre-rendered room views. Pinned favourites grid. Edit/delete diffs via `diffWords`.
- **Send failures surface in the UI**: Beeper bridges emit `com.beeper.message_send_status` events referencing the original encrypted event. Browser-side `src/matrix/sync.ts` flips `sendFailed` on the local echo and fires a notification. SUCCESS status clears any prior fail marker. Root cause of FAIL_RETRIABLE is almost always the hub device not being cross-signed — run `POST /matrix/keys/restore-cross-signing` (see Matrix recovery workflow below).
- **Force-rotate Megolm**: `matrix.rotateRoomKey({roomId})` RPC (→ `HubMatrixCrypto.invalidateRoomKey`) throws away the outbound session so the next send re-keys from scratch. Useful when a bridge gets into a wedged state. Note: `invalidateGroupSession` only touches the in-memory session, so we pre-load by calling `shareRoomKey(roomId, [], …)` first — otherwise after a hub restart the persisted stale session stays live.
- **Resume semantics (gap recovery)**: the hub runs one /sync loop and broadcasts `matrix.delta` over SyncBus — fire-and-forget, no per-client buffer. Reconciliation uses Matrix's **native** resumable-sync primitive: the client persists `next_batch` from every ingested delta (in `meta` table under `matrix:lastBatch`), and hands it back to the hub via `matrix.resume({since})` RPC on any wake signal. Hub calls `/sync?since=<token>&timeout=0`, decrypts, returns the delta directly (point-to-point, not broadcast). Trigger points all converge on a single debounced `reconcile()` in `src/hooks/useSync.ts`: (1) `hubBus.onConnect`, (2) `document.visibilitychange → visible` (critical for APK — the WebView pauses while backgrounded so WS stays "up" from JS's perspective and onConnect never fires), (3) `window.online`. `bulkPut` on event_id makes re-ingestion idempotent, so racing live-delta + resume is safe. If the homeserver rejects the `since` (expired), hub falls back to initial sync and flags `isInitial` on the response. `processJoinedRoom` gates `lastMessageBody`/`lastMessageTime` behind `advancesPreview` (newest-by-timestamp > existing) so out-of-order resume ingestion can't roll a room preview back to an older message. **A resume batch can carry an event AND its relation in one pass** — any relation handler (`m.replace` edits, reactions) must patch the in-flight `messages` array first and only fall back to `db.chatMessages.update` (which silently no-ops on a not-yet-persisted row; the `bulkPut` at the end then stores the pre-relation state).
- **Limited-timeline backfill**: Matrix `/sync` caps each room's timeline at ~10 events and sets `limited: true` + `prev_batch` when more happened during the gap. The APK WebView gets paused while backgrounded — on resume, its `since` token is far behind and sync returns many truncated rooms, so without backfill the local cursor jumps past real messages. Hub-side `backfillLimitedTimelines()` in `server/src/matrix/sync.ts` walks `/rooms/{id}/messages?from=prev_batch&dir=b` (limit 100) for each limited room, reverses to forward order, decrypts, and **prepends** the gap events before broadcasting the delta. Runs on both `resume()` (skipped on `isInitial`, since the full initial sync has no gaps) and `tick()` (live loop). Idempotent via `bulkPut(event_id)` client-side.
- **Redaction tombstones (bridges)**: WhatsApp / Signal delete events come through as `m.room.encrypted` with `content: {}` (the original ciphertext stripped) plus `unsigned.redacted_because.{sender,type:"m.room.redaction"}`. Without special handling they render as "🔒 Encrypted message" placeholders. Fix lives in `src/matrix/sync.ts`: `eventToMessage` returns `null` for tombstones, and `processJoinedRoom` has a pre-loop guard that flips any existing row's `isDeleted=true` + `deletedBy=<redactor>` when a tombstone for it arrives. Detect via `event.type === 'm.room.encrypted' && typeof event.content?.ciphertext !== 'string'`. **Explicit `m.room.redaction` events (Slack over Beeper) are a SEPARATE path with a pre-v11 shape**: hungryserv puts the target ONLY at the event's top level (`.redacts`), content is just `{reason}` — so the hub's field-by-field delta re-shape (`decryptJoinedRoomsWithCounts`) must preserve `redacts` on `MatrixEventLike` or every client loses the target. Client extraction is centralised in `src/matrix/redaction.ts` `redactionTargetId()` (content-first, top-level fallback); both client redaction handlers patch in-flight batch rows before `db.update`. When adding fields to the delta re-shape: it's an explicit allow-list — a top-level Matrix field not listed there is dropped for all clients.
- **Soft-delete-only guarantee (message archive)**: Console NEVER hard-deletes chat content — deletes by any party only ever mark rows `isDeleted`; original text + media stay recoverable. `server/src/matrix/message-archive.ts` (`MessageArchive`, `~/.config/console/chat-archive/`): append-only NDJSON per room (`events/<sha1(roomId)>.ndjson`, dedup-by-first-record so the pre-redaction copy wins) + `media/<sha1(eventId)>.bin` decrypted-attachment rescue. Wired in `MatrixSync.decryptJoinedRoomsWithCounts` (live sync) and `paginate` (history): every decrypted message-bearing event is archived BEFORE downstream processing; observing a redaction (explicit `m.room.redaction` or encrypted tombstone) triggers `recordRedaction` → downloads + AES-CTR-decrypts the attachment to disk (blobs outlive event redaction on Beeper). The archive class has deliberately NO delete/prune API. Surface: `chat-rooms.archivedEvent {roomId,eventId}` RPC (pre-redaction copy) + `GET /matrix/archive/media/<sha1>.bin`. SPA `DeletedMessageBody` in `ChatMessageBubble.tsx` renders deleted messages by falling back to the archive (struck-through original text, recovered image inline). Limit: content the hub never saw (deleted before Console ever synced the room) is unrecoverable — the homeserver strips it.
- **@-mention autocomplete** (`src/components/ChatComposeInput.tsx`). `@<query>` only opens the picker when the `@` is at start-of-input or after whitespace (so emails like `alice@example.com` don't trigger). Surviving `@DisplayName` tokens at send time become matrix.to anchor tags in `formatted_body` and userIds in an `m.mentions` block per MSC3952 — Element / Cinny / bridges treat the message as an intentional ping. Deleting the `@token` before send removes the userId from the m.mentions block. Room-members cache lives in `src/matrix/room-members.ts` (module-level, primed via `/matrix/rooms/:id/info`).
- **Hub Megolm backup upload (auto)**: on every boot, `server/src/index.ts` calls `hubMatrixCrypto.activateBackupUpload(homeserver, token)` which GETs `/room_keys/version`, extracts the public key, and calls `enableBackupV1(pub, ver)` — encryption-only, no recovery key needed. From that point on every new Megolm session the hub receives via to-device is auto-uploaded through `processOutgoingRequests` → `/room_keys/keys`, so a later hub re-init can restore everything. A one-shot `backupPendingRoomKeys()` sweep runs after activation to upload any sessions imported from the local M0 backup or received while backup was inactive. Boot log line: `[hub-crypto] backup upload activated (version N)` followed by `[hub-crypto] backed up N pending room keys` if any were outstanding.

### Calendar
- **Hub-proxied** — all API calls go through hub (`/cal/*`), which handles tokens server-side
- **Offline-first** — all mutations (create, update, delete, RSVP, reminder, location) are optimistic with sync queue
- **Temp IDs** — created events use `~timestamp.random` IDs, replaced with real Google IDs after queue processes
- **An optimistic calendar row is the ONLY copy of what the user typed until it reaches Google — every path that deletes calendar rows must exempt it.** `fetchEvents`'s stale-reap exempts queue rows in `pending`/`processing`/`failed`/`conflict` AND any `~`-prefixed temp id (`isTempEventId` — the guard that survives a reload); only calendars whose fetch FULFILLED are `reapable` (a rejected `allSettled` fetch is not "Google deleted everything"); a permanently failed `calCreate`/`calLocation` rolls back and toasts (`notifyFailure`); `CalendarEventForm` keeps the form open on error ("Retry"); Ctrl-refresh preserves `~`-id rows; `createEvent` passes `tempCompoundKey` as the hub `DedupStore` `clientToken`. Notes routes have no RouteContext carrying the bus, so `index.ts` injects a small `NoteOpenBridge` `{broadcast, clientCount}` literal at the call site (the `handleMicRoutes` `compose:` precedent). **GOTCHAs**: (1) `/notes/open` must be matched FIRST in `handleNoteRoutes` or the `/notes/file/` prefix matchers shadow it; (2) the receiver `src/notes/open-subscribe.ts` is wired at **boot in `GatedBoot`, NOT in NotesTab** — the vault adapter is only created on NotesTab mount and `openFile` early-returns `if (!adapter)`, so it calls `reconnectVault()` first; (3) the CM6 `editorView` isn't in the store until a frame or two after the pane switch, so it polls (`setTimeout`, 3 s cap — **never rAF**, see below). Anchor matching is case-insensitive against any heading level; unmatched → cursor stays at the top rather than guessing. Pure helpers `splitAnchor` (splits on the LAST `#`) / `findHeadingLine` unit-tested in `server/src/__tests__/notes-open.test.ts` + `src/__tests__/notes-open.test.ts`.
- **Remote-open into an ALREADY-OPEN tab — three rules**: (1) `requestAnimationFrame` does not fire in a backgrounded OR occluded tab (`document.visibilityState` still reads `"visible"` when merely covered), so `NotesEditorCore.mount()` races rAF against `setTimeout(…, 50)` with a `mounted` latch (the rAF must stay — it stops vim's `BlockCursorPlugin` calling `coordsAt` pre-layout) and the content-flush debounce is `setTimeout` too; never gate mount/flush/poll logic on rAF alone (`memory/project_raf_occluded_tab.md`). (2) The store's `editorView` slot is global — `setEditorView(view, path)` also stores `editorViewPath` and `waitForEditorView(path)` requires the match, or a mid-switch anchor dispatch scrolls the previous file. (3) An already-open tab holds the content read when it opened, and the caller has usually just written the file — `reconcileWithDisk()` re-reads and dispatches into the live view (setting `content` AND `savedContent`), opening an inline REVIEW rather than replacing when the copies differ (dirty buffer included — the user's text is the review base).
- **Open tabs are hub-backed, not localStorage** (`notesOpenTabs` pref; `persistTabs`/`loadPersistedTabs`/`restoreTabs` in `src/store/notes.ts`). The open-tab set is work-in-progress *context* — losing it is real loss — so the hub pref is authoritative and localStorage is only an offline mirror, read when the hub is unreachable at boot. Four load-bearing guards: (1) `restoreTabs()` awaits **`prefsReady()`** (raced against a 4 s timeout for tests / an unreachable hub) — reading the pref cache before `initPrefs()` resolves yields the empty default, and the next `persistTabs()` would write that emptiness over the real value; (2) `persistTabs` **no-ops the hub write while `!isPrefsLoaded()`** for the same reason (the local mirror still updates, and the next write after prefs land syncs); (3) a module-level `restoring` latch suppresses the per-`openFile` writes during a restore, so a reload landing mid-restore can't truncate the pref to however many tabs had re-opened — one write at the end, which also drops paths that no longer exist; (4) **`reconnectVault()`'s hub-adapter branch needs its own `restoreTabs()` call** — it doesn't go through `loadVaultFiles()`, so before this a hub-adapter boot came up with zero tabs regardless of what was persisted.
- **Mobile vim**: off by default (`console:notes:mobileVim` localStorage); auto-enables on hardware-keyboard heuristic (real Escape / Ctrl-chord keydown — soft keyboards emit keyCode 229/'Unidentified'); manual toggle = tappable "vim" chip in the editor status bar.
- **Live pen pages** (Neo smartpen → Notes): the APK forwards each BLE event as `pen_frame{kind:'dot',hex}` over `/push`; `server/src/pen-hub.ts` decodes via the pure `server/src/pen/page-codec.ts` and `server/src/pen/page-assembler.ts` assembles strokes into per-Ncode-page SVGs at `scratch/pen/<note>/page-<page>.svg` (the lossless `PenPageDoc` rides in `<metadata><penpage>{json}</penpage></metadata>`), broadcasting SyncBus service `pen` (`page_open`/`stroke_delta`/`stroke_end`/`page_saved`). ### Feeds
- Server-side RSS/Atom fetching. Offline reading via IndexedDB. OPML import/export.
- Optional full-text extraction via Readability. 15-min refresh interval.
- **Hidden folders** (`HIDDEN_FOLDERS` in the pure `src/feeds/hidden-folders.ts` — pure so node-env tests can import it without Dexie; case-insensitive): a folder whose feeds are excluded from the aggregated **"All"** list AND from the `totalUnread` badge, surfacing only when that folder/feed is opened directly. For high-volume/low-signal sources that would otherwise drown the main list. **Two edits are required and it's easy to ship half of it**: the filter in `loadItemsFromDb`'s `feedIds === null` branch (the "All" query — the per-feed and per-folder branches must stay unfiltered or direct navigation breaks) and the `total++` guard in `computeUnreadCounts` (per-feed `counts[]` still increment, so the folder shows its own count). The unified Inbox pane's Feed column also suppresses these (see Inbox section — `hiddenFolder` flag + `feedMode`).
- **`FeedSubscription.viaProxy`** — per-feed opt-in to fetch through a Cloudflare Worker instead of directly, for sources that **region-gate their RSS** (some 302 to an interstitial that then 404s; cookies, `old.` subdomains, and spoofed `CF-IPCountry` headers all fail because the gate is applied at the edge by requester geography, not by request content). The Worker is hostname-allow-listed + `x-proxy-secret`-authenticated; `REDDIT_PROXY_URL`/`REDDIT_PROXY_SECRET` live in `server/.env` (uncommitted) — absent config just fails those feeds rather than breaking the hub.
  - **`[placement] region = "aws:us-east-1"` in `wrangler.toml`, NOT `mode = "smart"`.** Smart placement optimizes *backend* latency and leaves execution at the PoP nearest the requester, so the outbound fetch still egresses locally and the gate still applies. Verify with the **`cf-placement` response header** — `local-LHR` means it didn't move, `remote-IAD` means it did. This distinction cost a debugging cycle.
  - **`rss-parser.parseURL` cannot be proxied** — it fetches internally. Proxied feeds must `fetch` the text themselves and use `parseString`.
- **Reddit comments** (`FeedStore.fetchRedditComments` → `GET /feeds/reddit-comments?permalink=`, rendered by `RedditComments` in `FeedItemView.tsx` for any Reddit item, mirroring the HN thread UI): Reddit serves a thread as Atom at **`<permalink>.rss`** — entry[0] is the OP (`t3_*`), the rest are comments (`t1_*`). **Flat, with no depth/parent field**, unlike HN's Firebase tree, so it renders as a flat list — don't try to reconstruct nesting from it. `?sort=top` is honoured server-side. **No upvote count is obtainable anonymously**: RSS/Atom omits `score`/`ups` entirely and the JSON API that carries them 403s without login, so ordering is the only signal available. Direct fetch first, proxy only as fallback.

### Property search (`con map property`) — multi-portal house-hunt poller
Cross-cutting invariants only — **the mechanics (inventory + kind layers, portal clients, dedupe, enrichment + farmland classifier, place filter, tenure, review state, backfill, nearest-airport, notify layer/criteria, two-tier bar, every portal's protocol traps) live in the `property` skill** (`.claude/skills/property/SKILL.md` — auto-loads when you touch `server/src/property/**` or the property CLI/SPA files; otherwise `Read` it). - **`--max-rings N` means the N LARGEST-by-area rings**, not "the first N" or "enough to cover the area": `outerRings()` sorts largest-first, `ringsInCountry()` filters to one country, `sync.rings()` slices to `maxRings`. Any ring past the cutoff is never queried, silently — no truncation flag, no log line, just fewer matches. Set `--max-rings` to the country's real ring count (`ringsInCountry`, or bump it until `count` stops changing).
- **Hub** `server/src/property/`: `types.ts` (the portal-agnostic `Criteria`/`Listing`/`PortalClient` contract WE own), `geo.ts` (polyline encode + `simplifyToLatLng` + `ringsInCountry` — each portal wants the same polygon in a different wire format), one client per portal, `store.ts` (`PropertySearchStore` → `~/.config/console/property-searches.json`), `sync.ts` (`PropertySync`, **hourly**, 30 s deferred first tick, `running` guard — modelled on `FlightSync`), `waf-token.ts`.
- **Alert-storm guard**: a search's first poll only **seeds** (`seeded` flag + `seenIds`, cap 4000, oldest-evicted) and fires zero notifications; later polls alert only on ids not in `seenIds`. `store.update()` **clears both whenever `criteria`/`layer`/`country` change**, so editing a search re-seeds instead of alerting on hundreds of pre-existing listings.
  - **The guard fires on changes to the `PropertySearch` record, NOT on the content of a layer it points at** — repainting the same `layer` slug with new geojson leaves `seenIds` stale and every newly-in-scope listing reads as "new" (alert storm). `PropertySync.reseed(id)` / `POST /property/searches/:id/reseed` / `con map property reseed <id>` clears `seeded`/`seenIds` without touching criteria — run it whenever a referenced layer's geojson is replaced, before the next poll.
- **`unsupported` + post-filter contract**: every client returns the criteria its portal *couldn't* express; `sync.postFilter()` re-applies **only those** locally. Never re-check a filter the portal already applied — listings that simply don't expose the field would get dropped.
- **Sparse-field filters belong in `unsupported`, not in the query.** A portal's server-side filter drops every listing that *omits* the field; ours keeps them. Rightmove reports a floor area on only **~49%** of rows, so `minSize`/`maxSize` are deliberately never sent — `minFloorArea` is declared unsupported and post-filtered. Same for plot area on UK/IT.
- **One bad ring silently kills the whole poll.** `pollSearch()` wraps the entire per-search fetch in a single try/catch — a throw from ring 4 of 18 discards rings 1–3's results too, `lastTotal`/pins stay stale, and the only trace is one hub log line. - **Queued messages — "send when the WHOLE turn is done"** (`Session.queuedMessage` + `queueMessage`/`setQueuedMessage`/`flushQueuedMessage`/`flushIfIdle`). Distinct from **steering**: writing to the CLI's stdin mid-turn lands at its next *tool boundary*, so anything held client-side and released on a timer would interrupt the turn. The queue therefore lives **hub-side**, which also makes it survive a page reload, the phone backgrounding, and a hub restart mid-turn (`ManifestEntry.queuedMessage`, restored via `SessionOptions`). **ONE buffer that grows** (Yousef's call, not a FIFO): a second queue appends blank-line-separated and the whole thing arrives as a single prompt. **Four flush points, all needed**: (1) `handleResultMessage` — the normal turn end; (2) the **interrupt-resume branch of the `exit` handler**, which emits a *synthetic* `result` via `emitHub` and so bypasses `handleResultMessage` entirely (without this an interrupt strands the queued prompt until some later turn ends); (3) inside `queueMessage` via `flushIfIdle()` — queueing on an idle session is just sending; (4) the `index.ts` restore loop for a queue restored onto an *idle* session (`setTimeout(…, 1_000)`, matching the nudge delay). A `wasRunning` session needs none of these — its restart nudge re-runs the turn and flush (1) fires at its end. **Do NOT flush from the constructor** — it races the "hub was restarted, continue" nudge and converts the queued prompt back into steering. `flushQueuedMessage` clears the slot **before** `sendMessage` (which flips status to `running`) or a re-entrant flush double-sends; it logs the prompt so the transcript shows it. `kill()` drops the queue. The `session_queued` broadcast bypasses `emitHub` (which logs everything but `status`/`tool_input_delta`) via a direct `this.emit('hub_message', …)`, exactly like `scanForAttention` — it's ephemeral state, not transcript, and is deliberately absent from `LoggableHubMessage`; the authoritative value rides `SessionInfo.queuedMessage`. Hibernation needs no special case (`sendMessage` is already hibernation-aware, so a flush wakes the session). Surface: protocol `queue_message`/`set_queued_message` → `session_queued`; store `queueMessage`/`setQueuedMessage`; UI in `AgentPromptInput.tsx` — **Ctrl/Cmd+Enter** queues (falls through to a plain send with no active session; **Shift+Enter is now the only newline**), a `Clock` chip above the composer shows the pending text with click-to-edit (pulls it back into the textarea and clears the queue, so re-queueing replaces rather than doubles) and an X to cancel, and while running the button cluster is `[Square (interrupt), Send]` where the Send **tap steers now** and **long-press (500 ms) queues** — that's the mobile trigger (`longPressFired` swallows the click that follows a fired press).
- **Idle hibernation** (`Session.hibernate()` + sweep in `index.ts`, 5-min cadence). Every live `claude` subprocess holds ~250MB RSS even idle. Sessions idle >30min get their subprocess SIGKILLed (`hibernating` flag → exit handler flips `hibernated`, status stays `idle`, messageLog/unread/claudeSessionId intact — NO `session_ended`); the next `sendMessage` transparently re-spawns with `--resume` (a message racing the SIGKILL is queued in `pendingWakeMessage` and delivered after wake). **Restore-into-hibernation**: the hub-restart restore loop passes `hibernateOnStart` for idle sessions (`!wasRunning`, Al exempt) so a restart spawns ~zero subprocesses instead of thundering 40+. Guards: `canHibernate()` blocks on running / pending approval (`approvalPending` — killing then would orphan the CLI's control_request) / model-restart in flight; `kill()` supersedes hibernation; model changes SKIP hibernated sessions (`restartForModelChange` no-op — the new model/pin resolves at wake since `spawn()` reads `modelOverride ?? resolveAgentModel()` fresh). `SessionInfo.hibernated` → moon glyph in the session list. Al never hibernates (always-on front door). **Pruned-transcript wake**: the CLI's retention can delete an old session's JSONL from `~/.claude/projects/` — `--resume` then prints `No conversation found with session ID: …` on stderr and exits(1) pre-init, which the exit handler misread as a model failure. stderr now sets `resumeTargetMissing`, and the exit handler respawns FRESH (no `--resume`; hub-side log/name/key kept; the CLI mints a new claudeSessionId at init) and re-delivers the waking message via `lastStdinPrompt` (captured in `sendMessage` — the original write went to the dying process). The user sees one error line explaining the model lost its old context.

The compaction levers are `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (window — a context-for-cost trade, Yousef's decision), `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, `CLAUDE_CODE_COLD_COMPACT`, `CLAUDE_CODE_DISABLE_PRECOMPACT_SKIP`, `DISABLE_AUTO_COMPACT`/`DISABLE_COMPACT`. Measured options (`scripts/context-clearing-sim.py`, full write-up in `docs/context-cost.md`): compact-at-fork-spawn (shipped — see Boards), wake-time Bash-result clearing (~10 % of cache_read, needs a hub-side transcript rewrite before `--resume`), per-fork auto-compact window — the last two are unbuilt design decisions. Re-run the sim after a week to measure.
- **Prompt-cache TTL is chosen per spawn** (`server/src/agents/cache-ttl.ts`). Claude Code reads `CLAUDE_CODE_PROMPT_CACHE_TTL` (`5m` | `1h`) once at process start; unset = 5m on Bedrock (its own doc string), so every hub session ran a 5-minute cache and a quarter-plus of cold-rewrite spend was the cache lapsing mid-work (^odd-toad's 7-day request-stream simulation: all-1h costs MORE — 1h writes bill 2× — but a per-session choice saves ~$400/wk). Verified 2026-09-08 that Bedrock honours the env var alone: `usage.cache_creation.ephemeral_1h_input_tokens = 37728, ephemeral_5m = 0` on the real Fable 5.1 profile with it set, the reverse without; `ENABLE_PROMPT_CACHING_1H_BEDROCK` is NOT needed. Note `status` is `'running'` on every fresh instance and says nothing at spawn time — never derive the TTL from it. Every spawn logs `[cache] <name>: prompt-cache TTL 1h (mid-turn)`; `SessionInfo.cacheTtl`/`cacheTtlReason` show the current process's (absent while hibernated). **Measurement**: `CacheTtlLedger` (`~/.config/console/cache-ttl-ledger.json`, atomic, local-day buckets) counts the CLI's own `usage.cache_creation.ephemeral_{1h,5m}_input_tokens` + reads + spawns per class from every `result`; `GET /dashboard/costs` ships it as `cacheTtl` (optional — older hub → absent) and the Costs card renders one "Cache writes 1h X (N%) · 5m Y · reads Z · spawns" line. Cost Explorer can't split the two write classes, the CLI can. Subagent TTL (`CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`) is deliberately left unset (5m — subagents are short bursts).

Clients only do the optimistic local half.

- **Agent-to-agent forks** (`con agent chat`). Spawns a fork of a named session, injects a message, waits for the reply, prints `conv: <claudeSessionId>` then the reply text. Follow-up turns: `con agent chat --id <conv-id> "<message>"` routes via the fork's claudeSessionId (survives hub restarts). The fork is a real hub session — visible in `con agent list`, tailable, appears in the SPA sidebar (nested under the parent with a `GitBranch` glyph). The target's MAIN session is untouched. Implementation: `cli/src/commands/agent.ts` + `cli/src/ws-client.ts` (`streamWithSends`, `injectAndCapture`).
- **`--end` marks the fork ended (readable), doesn't delete it.** `con agent chat --id <conv-id> --end` sends `kill_session`: it terminates the fork's subprocess and sets `status: ended` but **keeps the entry in `con agent list`** so the conversation stays readable (Yousef's call — no auto-reap). To fully remove a fork from the list, `con agent kill <session-id>` (`delete_session`). Both apply their dup-guard to EVERY session sharing the `claudeSessionId` (a resume during a restart can spawn a twin), and `Session.kill()` sets `status:ended` unconditionally (not only when a live process exists).
- **Hub restart reaps the previous generation's `claude` children before resuming anything** (`server/src/agents/process-reaper.ts`). pm2 restarts the tree with **SIGINT** (a claude child EXITS on it — see `midTurn` below) and the old `shutdown()` SIGTERMed children then `process.exit(0)`ed in the same tick, so anything that had not yet acted on the signal reparented to init with a dead stdio pipe and a LIVE tool loop. Three defences: (1) **boot reap** — the restore loop + AL bootstrap now run inside an async IIFE that first awaits `reapStaleProcesses()` (SIGTERM → 2 s grace → SIGKILL, each reap logged `[reaper] ended stale claude pid …`); (2) **`StaleProcessSweeper`** — 60 s timer, stale twins older than a minute get SIGTERM on first sighting and SIGKILL on the next; (3) **shutdown ends children before exiting** — `Session.terminateForShutdown()` SIGTERMs WITHOUT touching session state, `shutdown()` waits ≤1 s (`waitForExit`) then SIGKILLs survivors, then exits (pm2 `kill_timeout` is 1.6 s — keep the sequence under it). **A stale twin** = argv names `claude` AND carries the hub stdio signature `--input-format stream-json` AND ppid ≠ hub, AND either its env `CONSOLE_HUB_PID` (stamped on every spawn since this landed) names a pid that isn't us, or — for pre-marker processes — its argv names a csid we own: `--session-id <own>` (forks since 2a36c43a) or `--resume <x>` (`csidRefs` → `classifyStale`, pure, unit-tested). Yousef's interactive `claude --resume <csid>` in a terminal has no stream-json flag and is never touched; non-claude processes that merely inherited the marker (an agent's vite, zsh) are ignored. GOTCHAs: a **fork's `--resume` names its PARENT** (`--resume <parent> --fork-session [--session-id <own>]`; pre-2a36c43a forks carry no own id at all) — ownership is tested against every csid in argv and the ppid guard keeps live forks (our children) out regardless, but never assume a process's `--resume` IS the session it serves (`servedCsid`/`describeCsid` report `<parent>+fork` for the legacy shape). **Shutdown must not use `kill()`**: it sets `endedByUser` → the hub's `session.on('exit')` → `saveManifest` would persist `ended: true` for every session and the next boot would skip them all. `kill()` itself now escalates SIGTERM → SIGKILL after 5 s (`KILL_ESCALATE_MS`) so an ended session can't keep a live process either. `/proc` is read directly (Linux-only by design). Verify a restart with `ps -eo pid,ppid,args | grep -- --resume`: exactly one process per session, all with ppid = the hub.
- **Manifest** (`~/.claude/console-hub-sessions.json`, written by `server/src/manifest.ts`): the list the hub uses to re-spawn sessions at startup. Every write is **synchronous and atomic** (`writeFileSync` to a `.tmp` sibling, then `renameSync`) — no in-memory debounce buffer, so a SIGKILL or host crash can't lose pending state. Every session with a `claudeSessionId` is persisted regardless of `status` (yes, including `ended`); removal is driven only by `delete_session`, not by subprocess lifecycle. Subprocess lifecycle can therefore never prune sessions. If you ever need to manually rebuild the manifest from JSONL transcripts on disk: the hub clobbers external writes within ms of any session event, so the only reliable path is **write the new manifest then `SIGKILL` the hub in the same Node tick** (the shutdown handler also calls `saveManifest`, so SIGTERM would still clobber); pm2/tsx will respawn the hub and it'll load the new manifest cleanly. **SIGKILL the node process actually holding :9877 (`ss -tlnp`), NOT the pm2 wrapper pid** — killing the wrapper leaves the old hub serving while pm2's respawns crash-loop on EADDRINUSE, and one old-hub save wipes the edit (tell: a route the new code removed still answers 200).
- **`wasRunning` must come from `Session.midTurn`, never from `status`**. pm2 restarts the hub with **treekill: SIGINT reaches the claude CHILDREN too, and a claude child EXITS on SIGINT** (measured: `kill -INT <child>` → process gone, hub's exit handler runs with `shuttingDown` still false → `status = 'ended'`). Those child exits routinely land *before* the hub's own signal handler, so a manifest keyed on `status === 'running'` recorded every mid-turn session as not-running: they restored hibernated and silent, and **nobody got the "The hub was restarted, which interrupted you. Continue." nudge**. `midTurn` is the durable shadow of a turn: set in `sendMessage`, cleared ONLY by a real `result` or a user `interrupt()` — never by a process death, which is the entire point. `shutdown()` also calls `session.markShuttingDown()` for every session *before* saving, so a child dying during the save can't flip state either. When touching this path: a lost nudge is invisible (nothing errors, agents just sit), so assert on BOTH ends of the log — `Shutting down — saving manifest (N mid-turn: <names>)` names what the old process saved, and `Resumed + continued:` must appear for exactly those on the restore side. **The subtle leak: SIGINT mid-tool-call makes the CLI emit `result/error_during_execution is_error=true` and THEN exit 0** — that result reached `handleResultMessage` before the exit and cleared `midTurn`, so `markShuttingDown()` froze an already-cleared bit. Error results (`is_error` or `subtype` starting `error`) no longer clear `midTurn`; only a success result or `interrupt()` does. Probe recipe: spawn `claude -p --output-format stream-json --input-format stream-json --verbose --dangerously-skip-permissions --model haiku`, send a user message that runs `sleep 40` via Bash, `kill('SIGINT')` 3 s after the `tool_use`, log every stdout `type/subtype` until exit. **Anything computed at SHUTDOWN needs TWO restarts to observe**: the restart that deploys the change still runs the OLD process's shutdown, so its manifest carries the old derivation. The first real test is the restart after the deploying one.

### Hub-side agent cron (`/cron/*`)
Claude Code's built-in `/loop` / `CronCreate` is session-scoped and DOES NOT survive hub restarts under our SDK transport (`--input-format stream-json`) — empirically verified, matches Anthropic bugs [#40228](https://github.com/anthropics/claude-code/issues/40228) (`durable: true` doesn't persist) and [#40081](https://github.com/anthropics/claude-code/issues/40081) (sessions with cron tasks vanish from `/resume`). So the hub runs its own.
- **Scheduler**: `server/src/cron/scheduler.ts` (Croner + debounced JSON persist to `~/.config/console/agent-cron.json`). Tasks keyed by `claudeSessionId` (stable across restarts; hub session ids are rejected). Forks get a new claudeSessionId so they inherit zero tasks. **A csid is stable across hub restarts, hibernation wakes, `con agent reload <session>`, model/backend respawns — all `--resume`. Exactly two paths mint a NEW csid for an existing session, and both now re-key that session's active crons via `reassignSession`: (1) `con agent reload AL` (fresh persona spawn by design — `reloadAlSession` captures the old csid and re-keys on the new `session_init`); (2) the pruned-transcript fresh respawn (`session_init` carries `rekeyedFrom` when a pre-set resume csid differs from what the CLI minted; the `hub_message` listener in `routes/agents.ts` re-keys).** Fires by mirroring the post-restart "Continue." nudge path: `broadcast(user_prompt) + session.logMessage + session.sendMessage`. Auto-disables a task after 10 consecutive misses (session not found / ended). One-shot tasks self-remove after firing. Croner `protect: true` prevents overlapping fires when Claude takes longer than the cron interval to respond.
- **Guard scripts (token-free polling)**: a task may carry an optional `guard` — a shell command run (via `bash -c` in the session's cwd, 60 s cap) at **every** trigger, BEFORE any agent wake. `fire()` is async: it runs the guard first and only proceeds to `sendMessage` when the guard **exits 0**; a non-zero exit is the normal "nothing to do" case — skipped silently, **no tokens spent**, task stays scheduled. The guard's stdout (trimmed, 4 KB cap) is appended to the wake prompt (`\n\n--- guard output (\`<cmd>\`) --- \n…`) so the agent knows *what* changed. This is how "wake only when X changed" works with zero cost between changes — e.g. a script that curls a URL, diffs against a saved copy, and `exit 0` only on change. **Guard skips do NOT count toward the 10-miss auto-disable budget** (a guard saying "no change" for months is working, not failing); only session-not-found/ended does. Guard stdout is transient (`guardOutput`, stripped from the persisted JSON); the guard command itself persists and survives restarts. Surface: `POST /cron {…, guard}`, CLI `con cron add … --guard "<cmd>"` or `--guard-file <path>`. **`--guard-file` INLINES the file's contents into the cron record** (the path is not referenced), so later edits to the script don't propagate — remove + re-add the task, or use `--guard "bash ~/exec/x.sh"` when you want the file to stay live. `runOnce`/`con cron run` also evaluates the guard (a manual run of a guarded task only wakes if the guard passes).
- **Routes** (`server/src/routes/cron.ts`): `GET /cron[?session=…]`, `POST /cron`, `DELETE /cron/:id`, `POST /cron/:id/run`, `GET /cron/upcoming?n=N`, `GET /cron/ics-token` (returns `{token, publicUrl}`), `GET /cron.ics?token=…` (constant-time compare; 403 on bad token; `Cache-Control: max-age=300`).
- **ICS**: `server/src/cron/ics.ts` expands each task into discrete VEVENTs (next 50 firings, 30-day window) via `Croner.nextRun()` — avoids the lossy cron→RRULE conversion. UTC timestamps, RFC5545 line folding + escaping. Calendar clients re-fetch periodically.
- **CLI**: `con cron list/add/remove/run/upcoming/ics-url`. `--trigger` accepts a 5-field cron, ISO datetime, or `+30m`/`+2h`/`+1d` (CLI resolves relative to ISO). `--once` flips recurring=false (implied for ISO/relative).
- **SPA**: `src/components/agent/CronPill.tsx` (status-bar chip) + `CronPanel.tsx` (side panel: list, run-now/delete, recurring/one-shot create form with live validation, ICS subscription URL with copy). Backed by `src/store/cron.ts` (polled, no WS sync in v1).

Deduped on the board itself: an OPEN card (any column but Done) whose text starts with `Ring miss: "<same transcript>"` means no new card (`route.card` in the sidecar records `filed|exists|failed`). `kind:'unknown'` (no fallback configured) is a choice, not a miss — no card. Unclaimed text still goes to the AL fork, whose seed asks IT to judge whether a `Ring schema gap` card is warranted. Latency: rules are µs; hub STT 1–3 s only when the ring sent no transcript; the LLM classifier ~10–15 s only on a rule miss (`llm_fallback: false` skips it).

### Push-to-talk (PTT) — system-wide hold-to-talk → STT → mic owner
A hardware/hotkey hold-to-talk that streams mic → hub `/stt` (OpenAI realtime, `{type:'audio',data:b64}` → `{interim|final,text}`) and on release routes the transcript to the **mic owner** session. Owner model in `server/src/mic.ts` (`MicState`: `ownerSessionId` persisted to `mic-owner.json`, transient `hot`); routes in `server/src/routes/mic.ts` (`/mic/status|owner|hot|say|compose`); SyncBus `mic` service in `index.ts` broadcasts `state` (owner/hot) + `compose` (transient, NOT in the subscribe snapshot — and the SyncBus never replays missed events). Default owner = explicit-if-live-else-Al. CLI `con mic status|give|pass|release|say|ptt`. SPA mirror in `src/store/mic.ts` + the `MicButton` in Spaces.
- **Two delivery modes**: `/mic/say` = inject + **auto-send** to the owner; `/mic/compose` = drop into the owner's composer **unsent** for review (`AgentPromptInput` reacts to `composeSeq`). A composed draft **lingers** in the textarea until sent/cleared — by design (it's a review draft), so an earlier foreground compose can still be sitting there later; it is NOT a duplicate of a backgrounded `say`.
- **Desktop** (Sway) PTT is REMOVED (^lean-duck) — the bindings, `~/exec/con-ptt*`, the `foot` popup and the waybar indicator are gone; never re-add them. Hub `/stt` + `/mic/*` stay (SPA, APK, CLI use them).
- **Phone** (APK v26+): the rugged phone's Custom-key **"Open Zello"** Easy-shuttle mode is the ONLY one that emits the firmware-level `com.zello.ptt.down/.up` broadcasts (Zello PTT API action strings — independent of any app). `PushService.pttReceiver` records on `.down` (AudioRecord VOICE_RECOGNITION 24kHz mono PCM16 → `/stt`), and on `.up` routes to `/mic/compose` if `MainActivity.foreground` else `/mic/say`. Needs FGS type `microphone` + RECORD_AUDIO. The native service requires the **apk bearer** (pair the APK) — see [Known Issues] + `memory/project_android_js_bridge_bind.md`.
- **Two STT models, deliberately NOT one constant** (`server/src/stt.ts`). The realtime endpoint (`wss://…/v1/realtime?intent=transcription`) and the batch endpoint (`POST /v1/audio/transcriptions`) reject each other's model ids, so they need separate constants — `STT_MODEL = 'gpt-realtime-whisper'` (streaming: PTT, dictation, glasses mic) and `STT_BATCH_MODEL = 'gpt-transcribe'` (whole-file: `/stt` upload endpoint + Al's WhatsApp voice notes). A test in `__tests__/stt.test.ts` pins `STT_BATCH_MODEL !== STT_MODEL` so a "consolidate these" refactor fails loudly. **`gpt-live-transcribe` is REJECTED** (A/B-tested: measurably worse transcripts; and `server_vad` breaks the explicit `input_audio_buffer.commit`) — don't retry it. **When probing the realtime endpoint, stream at true realtime pace (4800-byte chunks / 100 ms at 24 kHz mono PCM16)** — faster starves the streaming decoder and garbles every model, invalidating the comparison.
- **A turn only ends because the CLIENT says so — `{type:'done'}` on mic release** (`server/src/index.ts` `/stt` handler; `STT_FLUSH_IDLE_MS` / `STT_DONE_TIMEOUT_MS` in `stt.ts`). `gpt-realtime-whisper` **rejects `turn_detection`**, so nothing closes a turn on its own: it streams deltas lazily and the tail sits unemitted for 5–8 s. Two commit triggers, and **neither is a wall-clock timer** — that distinction is load-bearing, since periodic commits chop mid-sentence and were vetoed for wrecking accuracy (`memory/feedback_stt_no_periodic_commits.md`): (1) **idle** — every `append` resets a `STT_FLUSH_IDLE_MS`=600 ms timer, so a commit only lands in a genuine gap; (2) **`{type:'done'}`** — commits immediately, then the relay holds the socket open until the `final` lands and **closes it itself** (capped by `STT_DONE_TIMEOUT_MS`=4 s so a stuck turn can't strand the mic UI). Measured commit→`final` ≈ 600–700 ms.
  - **The START of the turn is guarded too: no audio is dropped during either handshake.** Two rules: (1) the hub relay silently discarded frames arriving while the OpenAI WS was still CONNECTING (~0.5–1.5 s TLS+WS) — it buffers them (`pushCapped` in `stt.ts`, oldest-evicted at `STT_PREBUFFER_MAX_BYTES` ≈ 30 s) and flushes on open, with a `done`-during-handshake committing right after the flush; (2) `useDictation` serialized getUserMedia → WS open → only then built the capture graph, so the browser wasn't even recording until the client WS opened — capture now starts immediately with its own pre-open frame queue, and the WS + getUserMedia open concurrently. The Kotlin paths need nothing (OkHttp queues `send()` before the connection opens). Also: a browser whose SpeechRecognition fails with `network`/`service-not-allowed` (Brave) burns seconds discovering it per dictation — `console:dictation:hubOnly` localStorage remembers the failure and goes straight to hub STT forever after.
  - **Three independent implementations, all of which must send `done` and wait** — a fix to one is a fix to none of the others: `src/hooks/useDictation.ts` (SPA + APK WebView), `android/.../core/Dictation.kt` (native composer mic), `android/.../PushService.kt` `pttUp()` (hardware PTT key).
  - **Android dictation is a process singleton with an OWNER**: `Dictation.start(owner?)` tags `State.owner`, and `committed` emits `Commit(text, owner)`. The on-screen `Composer` collects `committed` unconditionally (that's how the hardware PTT key lands text), so any OTHER field that dictates — `ui/components/DictatedTextField` (approval-card answer + plan-comment) — must start with its own owner id; the Composer masks owned state (`owner != null` → plain Mic, no transcript, commit skipped). Without the tag a dictated answer lands in BOTH the field and the composer draft. A new dictating surface = a `DictatedTextField`, never a raw `Dictation.start()`.
  - **The `final` carries the WHOLE turn, so it supersedes the accumulated deltas** — appending it duplicates the utterance. The Kotlin paths replace rather than append; the SPA instead *suppresses* the final when deltas already covered it (`sawDeltaRef`), and that flag must **not** be reset in the teardown path — the final arrives *after* `stop()`.
- **`android/zello-shim/`** — a tiny invisible stub app with applicationId **`com.loudtalks`** (Zello's REAL package — `com.zello` is only the broadcast prefix). "Open Zello" deep-links to the Play Store when `com.loudtalks` is absent; installing this no-op (a translucent activity that finishes instantly) makes the firmware's launch resolve to nothing visible while the PTT broadcasts keep firing. Build `./gradlew :zello-shim:assembleDebug`, served at `/public/apk/loudtalks-shim.apk`.

### Sending WhatsApp from a sibling agent
Use `con whatsapp send <to> --body "..."`. The CLI carries an `al`-scoped bearer when enforcement lands.

- `con whatsapp send <to> [--body "..." | --file <path> | --stdin]` — outbound text. `<to>` is bare phone (auto-suffixed `@s.whatsapp.net`) or fully-qualified JID (`<n>@s.whatsapp.net`, `<lid>@lid`, `<id>@g.us`).
- `con whatsapp delete <message_id> --to <jid>` — revoke for everyone; WhatsApp silently ignores past ~48 h.
- `con whatsapp contacts [--query <text>]` — workspace lookup; source = `~/.local/share/al/workspace/users/*.md`.
- `con whatsapp qr [--out <path.png>]` — fetch current pairing QR; 404 when paired.
- `con whatsapp status` — `{connected, hasQr}`.

The CLI is the preferred path. If a sibling agent needs Al's interpretation / context, `con agent chat "AL" "please WA Rowan saying X"` — Al sends, holds the thread, forwards replies.

### Inbound flow
Baileys `onMessage` (after `fromMe` filter) → `ensureUserKnown` → `inboundEnvelope(msg, resolvedUser)` → `injectToAl(envelope, broadcast)`. The envelope is **task-framed** (not a chat message) so Claude doesn't default to a silent in-session reply. Shape:
```
[INBOUND WhatsApp — action required]
From: <senderName> (<sender-jid>) — resolved user: <name or "unknown">
Thread: <jid>
Message ID: <wamid.HBgL...>

Message:
<body>

[Attached image(s) (Read these paths): /tmp/console-al-inbound/<id>-0.jpg]   ← only when an image is attached
[INBOUND WhatsApp] Attached file (audio, audio/ogg): /tmp/console-al-inbound/<id>-0.ogg   ← audio/video/document, any type
Voice note transcript: "..."   ← only for a ptt voice note (OpenAI preferred, Gemini fallback via GEMINI_API_KEY)

---
ACTION ... con whatsapp send <jid> --body "..."  (a session-only text reply is invisible to the sender)
```
Inbound images/audio/video/documents are all downloaded by `whatsapp.ts`, written to `os.tmpdir()/console-al-inbound/` (documents keep their real filename), and their paths injected into the envelope so Al can `Read` them (the text-only inject path can't carry bytes). Voice notes (audio + `ptt`) are additionally auto-transcribed via `al/transcribe.ts` and the transcript is inlined in the envelope — no OPENAI_API_KEY/GEMINI_API_KEY configured just skips transcription (never blocks delivery of the audio file itself). Voice delegate envelopes use a `[Voice delegate from ...]` header with explicit "reply will be spoken aloud" guidance.

### Conversation forks (per-thread routing — `al/conversation-forks.ts`)
**Non-owner WhatsApp threads no longer inject into Al's main session.** `routeInbound()` (wired in the `onInbound` handler before `injectToAl`) forks AL per thread JID (`AL ↔ <person>`, `--fork-session` off Al's claudeSessionId) and routes all later messages from that thread to the fork; **Yousef's threads always go to the parent** (`resolvedUser === 'yousef'` bypass — routing the owner through a digest-delayed fork would hollow out parent-Al). Why: privacy (concurrent conversations — e.g. Mai + Nica — never share a context window, so per-contact deny-walls become a physical boundary) + parent context hygiene. Mechanics: routing table persisted at `~/.config/console/al-conversation-forks.json` (atomic write; restored on boot by `startConversationForks`, which re-points hub ids the restore loop re-minted via claudeSessionId match and drops dead records); messages arriving during the fork's spawn gap queue in `pendingSpawns` and flush on `session_init` (the `--fork-session` no-init-until-first-input gotcha applies — seed + first envelope are sent immediately); fork spawn failure falls back to the parent (never drops a message). **Idle wind-down** (1 min sweep, 1 h idle): substantive conversations (>2 inbound msgs or marked substantive) digest-merge into the parent via `mergeIntoParent`; trivial ones reap silently (transcript survives on disk + chat archive — a digest of "thanks/np" isn't worth 2 turns); a mid-turn fork gets its deadline pushed, never interrupted. Unit-tested in `__tests__/conversation-forks.test.ts` (stubbed createSession/wakeSession/merge; forks file via `CONSOLE_AL_FORKS_FILE`).
- **A contact is one PERSON across two JIDs, and the thread alone can't show what they're replying to.** Al's sends go to whichever JID he picks (usually the phone `447…@s.whatsapp.net`); the reply often arrives from the linked-device `…@lid`. Label the IDENTITY at both ends, never restate history (quoting Al's last sends into every envelope was vetoed as heavy/redundant — the model already has the transcript, it just needs to know two names are one person): (1) the envelope's From line reads `resolved user: nica (same person as 447776912442)` (`identifiersFor(user)` minus the sender's own id, via `users.ts`); (2) `POST /whatsapp/send` returns `user: <resolved>` beside `jid`, so the send's tool result carries the same canonical name the inbound will; (3) `forkSeed` names the other identifiers as "the SAME PERSON". ~10 tokens per event. Tests in `__tests__/al-contact-identity.test.ts`.

### Read-only session peek (`con agent peek`, `GET /agents/peek`)
`con agent peek <session-id|conv-id|name> [--n 20]` — look at ANY session's conversation **without forking, injecting, or disturbing it** (safe mid-turn). Hub route resolves hub id → claudeSessionId → unique name (409 on ambiguity) and reads the transcript off disk via `loadSessionHistory` (the full record — `messageLog` is capped/replay-limited). Built so Al can introspect his conversation-forks ("is there a convo I'm not aware of?" — his AL.md points him at `con agent list` + `peek`); generally useful for auditing any agent conversation.

## Matrix recovery workflow (hub-side)
The browser "recovery key" flow is gone; recovery is hub-side (`server/src/matrix/backup-restore.ts` + `secret-storage.ts`): `POST /matrix/keys/restore-from-recovery-key`, `POST /matrix/keys/restore-cross-signing` (required after ANY hub re-login — bridges reject Olm from uncross-signed devices), `POST /matrix/keys/import-local-backup`, `POST /matrix/decrypt-event`. **"🔒 Encrypted message" placeholders in one room = a withheld Megolm session**; the fix needs NO user-supplied key (the hub's own seed in `matrix-crypto-snapshot.json` re-encodes to a valid `EsU…` key). The step-by-step runbook, the SSSS/keyId gotchas and the withheld-session recovery are the **`matrix-recovery` skill** (`/matrix-recovery`, user-invocable) — invoke it when messages won't decrypt or bridges drop sends.

## Debugging (PRIMARY METHOD)

**Use the embedded debug agent, NOT browser DevTools or Chrome MCP tools.**

The app has a built-in debug agent (`src/debug-agent.ts`) that streams all console output, network requests, and errors to the hub in real-time. Claude Code observes via HTTP endpoints:

```bash
# See recent events (console logs, network requests, errors)
curl -sk https://localhost:9877/debug/log?n=30

# Filter for errors
curl -sk https://localhost:9877/debug/log?n=100 | jq '.[] | select(.cat=="error")'

# Filter for failed network requests
curl -sk https://localhost:9877/debug/log?n=100 | jq '.[] | select(.cat=="net" and .status >= 400)'

# Execute JS in the browser (replaces Chrome MCP javascript_tool)
curl -sk -X POST https://localhost:9877/debug/eval -H 'Content-Type: application/json' -d '{"code":"document.title"}'

# Get Zustand store state
curl -sk https://localhost:9877/debug/state

# Check if debug agent is connected
curl -sk https://localhost:9877/debug/status
```

The debug agent:
- Captures from page load (imported first in `main.tsx`)
- Survives navigation (WebSocket auto-reconnects)
- Works across all tabs/devices (all stream to same hub)
- Logs to `~/.config/console/debug.log` (NDJSON, auto-rotated at 5K lines)
- `window.__console` (dev-only) exposes Zustand stores + Dexie db for browser console access

## Key Patterns

### Auth
- **Hub-managed OAuth** — all tokens stored server-side in `~/.config/console/auth.json`. Frontend bootstraps via `GET /auth/token`. Sign-in opens hub's `/auth/google/start` in a popup.
- **Multi-account** — hub stores multiple Google accounts. Calendar sidebar can add accounts via OAuth flow. **Adding an ADDITIONAL account must pass `?add=1`** to `/auth/google/start` — that switches `prompt` from `consent` to `select_account consent`. Without it Google silently re-consents whichever account the browser is already signed into, so "Add calendar account" just re-links the existing account and the new one never appears. The plain sign-in path deliberately stays `consent` (no chooser).
- **Token refresh** — hub proactively refreshes tokens 5min before expiry. Frontend re-fetches from hub on 401.

### Offline Sync Queue
- **Shared queue** — `src/db/sync-queue.ts` provides `enqueue()`, `markDone()`, `markFailed()` for all services
- **Action types** — email (`archive`, `send`, etc.), chat (`chatSend`, `chatMarkRead`), calendar (`calCreate`, `calUpdate`, `calDelete`, `calRsvp`, `calReminder`, `calLocation`)
- **Pattern** — optimistic IDB write → `set()` for instant UI → `enqueue()` → background processor flushes within 500ms
- **Retry** — 3 retries before marking `failed`. Queue survives page reload.
- **Undo** — delete actions show 5-second undo toast. Undo removes from queue + restores IDB.

### Email
- Optimistic archive/snooze with undo. Auto-archive on reply. Pre-rendered iframes. CID inline images.
- Snooze is local-only (Gmail has no snooze API). Conflict detection before sending queued replies.
- Send-as aliases fetched during sync. Calendar invites parsed from `text/calendar`.

### Chat (Matrix)
- **Hub-owned room snapshot.** The canonical view of every joined room (name, isUnread, unreadCount, avatar, memberCount, tags, snoozedUntil, lastMessage*) lives server-side in `server/src/matrix/chat-rooms-store.ts` (a `SnapshotStore` wrapper from `server/src/snapshot-store.ts`). Every `/sync` delta computes the row via `server/src/matrix/room-state.ts` (port of the SPA's old `processJoinedRoom` logic) and the store broadcasts on the `chat-rooms` service. Browser-side `src/matrix/chat-rooms-subscribe.ts` mirrors snapshot + deltas straight into `db.chatRooms`. Replaces per-device derivation — "mark read on PC → phone sees it" works without local divergence. RPCs registered under `chat-rooms`: `snapshot`, `markRead`, `markUnread`, `snooze`. **Manual unread is durable** (`RoomState.manualUnread`): a user "mark unread" has no homeserver concept, so `computeRoomState` previously cleared it on any sync reporting `notification_count=0` — and the big catch-up `resume`/sync after a hub restart touches enough rooms to wipe *all* manual markers at once. The sticky flag forces `isUnread` true across recomputes and is cleared only by an explicit `markRead` (`setRoomRead`); genuine notif-backed unread was never affected.
- Direct REST API (no matrix-js-sdk). E2EE via OlmMachine WASM. Long-polling sync.
- Local echo with `~timestamp.random` IDs. Bridge detection (WhatsApp, LinkedIn, Slack).
- Pre-rendered room views. Pinned favourites grid. Edit/delete diffs via `diffWords`.
- **Send failures surface in the UI**: Beeper bridges emit `com.beeper.message_send_status` events referencing the original encrypted event. Browser-side `src/matrix/sync.ts` flips `sendFailed` on the local echo and fires a notification. SUCCESS status clears any prior fail marker. Root cause of FAIL_RETRIABLE is almost always the hub device not being cross-signed — run `POST /matrix/keys/restore-cross-signing` (see Matrix recovery workflow below).
- **Force-rotate Megolm**: `matrix.rotateRoomKey({roomId})` RPC (→ `HubMatrixCrypto.invalidateRoomKey`) throws away the outbound session so the next send re-keys from scratch. Useful when a bridge gets into a wedged state. Note: `invalidateGroupSession` only touches the in-memory session, so we pre-load by calling `shareRoomKey(roomId, [], …)` first — otherwise after a hub restart the persisted stale session stays live.
- **Resume semantics (gap recovery)**: the hub runs one /sync loop and broadcasts `matrix.delta` over SyncBus — fire-and-forget, no per-client buffer. Reconciliation uses Matrix's **native** resumable-sync primitive: the client persists `next_batch` from every ingested delta (in `meta` table under `matrix:lastBatch`), and hands it back to the hub via `matrix.resume({since})` RPC on any wake signal. Hub calls `/sync?since=<token>&timeout=0`, decrypts, returns the delta directly (point-to-point, not broadcast). Trigger points all converge on a single debounced `reconcile()` in `src/hooks/useSync.ts`: (1) `hubBus.onConnect`, (2) `document.visibilitychange → visible` (critical for APK — the WebView pauses while backgrounded so WS stays "up" from JS's perspective and onConnect never fires), (3) `window.online`. `bulkPut` on event_id makes re-ingestion idempotent, so racing live-delta + resume is safe. If the homeserver rejects the `since` (expired), hub falls back to initial sync and flags `isInitial` on the response. `processJoinedRoom` gates `lastMessageBody`/`lastMessageTime` behind `advancesPreview` (newest-by-timestamp > existing) so out-of-order resume ingestion can't roll a room preview back to an older message.
- **Limited-timeline backfill**: Matrix `/sync` caps each room's timeline at ~10 events and sets `limited: true` + `prev_batch` when more happened during the gap. The APK WebView gets paused while backgrounded — on resume, its `since` token is far behind and sync returns many truncated rooms, so without backfill the local cursor jumps past real messages. Hub-side `backfillLimitedTimelines()` in `server/src/matrix/sync.ts` walks `/rooms/{id}/messages?from=prev_batch&dir=b` (limit 100) for each limited room, reverses to forward order, decrypts, and **prepends** the gap events before broadcasting the delta. Runs on both `resume()` (skipped on `isInitial`, since the full initial sync has no gaps) and `tick()` (live loop). Idempotent via `bulkPut(event_id)` client-side.
- **Redaction tombstones (bridges)**: WhatsApp / Signal delete events come through as `m.room.encrypted` with `content: {}` (the original ciphertext stripped) plus `unsigned.redacted_because.{sender,type:"m.room.redaction"}`. Without special handling they render as "🔒 Encrypted message" placeholders. Fix lives in `src/matrix/sync.ts`: `eventToMessage` returns `null` for tombstones, and `processJoinedRoom` has a pre-loop guard that flips any existing row's `isDeleted=true` + `deletedBy=<redactor>` when a tombstone for it arrives. Detect via `event.type === 'm.room.encrypted' && typeof event.content?.ciphertext !== 'string'`.
- **Soft-delete-only guarantee (message archive)**: Console NEVER hard-deletes chat content — deletes by any party only ever mark rows `isDeleted`; original text + media stay recoverable. `server/src/matrix/message-archive.ts` (`MessageArchive`, `~/.config/console/chat-archive/`): append-only NDJSON per room (`events/<sha1(roomId)>.ndjson`, dedup-by-first-record so the pre-redaction copy wins) + `media/<sha1(eventId)>.bin` decrypted-attachment rescue. Wired in `MatrixSync.decryptJoinedRoomsWithCounts` (live sync) and `paginate` (history): every decrypted message-bearing event is archived BEFORE downstream processing; observing a redaction (explicit `m.room.redaction` or encrypted tombstone) triggers `recordRedaction` → downloads + AES-CTR-decrypts the attachment to disk (blobs outlive event redaction on Beeper). The archive class has deliberately NO delete/prune API. Surface: `chat-rooms.archivedEvent {roomId,eventId}` RPC (pre-redaction copy) + `GET /matrix/archive/media/<sha1>.bin`. SPA `DeletedMessageBody` in `ChatMessageBubble.tsx` renders deleted messages by falling back to the archive (struck-through original text, recovered image inline). Limit: content the hub never saw (deleted before Console ever synced the room) is unrecoverable — the homeserver strips it.
- **@-mention autocomplete** (`src/components/ChatComposeInput.tsx`). `@<query>` only opens the picker when the `@` is at start-of-input or after whitespace (so emails like `alice@example.com` don't trigger). Surviving `@DisplayName` tokens at send time become matrix.to anchor tags in `formatted_body` and userIds in an `m.mentions` block per MSC3952 — Element / Cinny / bridges treat the message as an intentional ping. Deleting the `@token` before send removes the userId from the m.mentions block. Room-members cache lives in `src/matrix/room-members.ts` (module-level, primed via `/matrix/rooms/:id/info`).
- **Hub Megolm backup upload (auto)**: on every boot, `server/src/index.ts` calls `hubMatrixCrypto.activateBackupUpload(homeserver, token)` which GETs `/room_keys/version`, extracts the public key, and calls `enableBackupV1(pub, ver)` — encryption-only, no recovery key needed. From that point on every new Megolm session the hub receives via to-device is auto-uploaded through `processOutgoingRequests` → `/room_keys/keys`, so a later hub re-init can restore everything. A one-shot `backupPendingRoomKeys()` sweep runs after activation to upload any sessions imported from the local M0 backup or received while backup was inactive. Boot log line: `[hub-crypto] backup upload activated (version N)` followed by `[hub-crypto] backed up N pending room keys` if any were outstanding.

### Calendar
- **Hub-proxied** — all API calls go through hub (`/cal/*`), which handles tokens server-side
- **Offline-first** — all mutations (create, update, delete, RSVP, reminder, location) are optimistic with sync queue
- **Temp IDs** — created events use `~timestamp.random` IDs, replaced with real Google IDs after queue processes
- **Five silent data-loss paths in the create pipeline, all closed 2026-08-11** (found after a hand-written event with a description vanished; the Google-side forensic sweep — `updatedMin` + `showDeleted=true` across every calendar — proved it *never reached Google*, so the loss was entirely client-side. Note a deleted Google event **loses its `summary`**, so a keyword/`q=` query can never find a tombstone; `updatedMin` is the only usable sweep, and the hub's `/cal/events` can't do it at all since `calendar-client.ts getEvents` forwards no `showDeleted`). An optimistic row is the **only** copy of what the user typed until it reaches Google, so every path that deletes calendar rows must exempt it:
  1. `fetchEvents`'s stale-reap deletes any IDB event in the fetched range that Google didn't return. Its `pendingKeys` guard covered only `pending`/`processing` queue rows plus the **reload-volatile** module-level `pendingTempIds` map — so a create that failed 3× (→ `failed`) *or* any page reload left the temp row unprotected and the next fetch ate it. Now the status filter includes `failed`/`conflict` **and** there's a durable `isTempEventId` (`~` prefix) exemption, which is the guard that survives a reload.
  2. The per-calendar fetch is `Promise.allSettled`, but the reap ran unconditionally — a **rejected** calendar contributes nothing to `freshKeys`, which the reap read as "Google deleted everything here", destroying even successfully-synced events on any hub hiccup/401. Now only calendars in the `reapable` set (fulfilled fetches) may be reaped.
  3. A permanently-failed `calCreate`/`calLocation` had **no rollback branch and no notification** — total silence, indistinguishable from success. Now `notifyFailure` pushes a 30 s error toast naming the event title.
  4. `CalendarEventForm.handleSubmit` had zero error handling and always `closeEventForm()`d — the UI reported success unconditionally and threw away the typed text. Now a `saveError` state keeps the form open with the content intact and relabels the button "Retry".
  5. Ctrl/Cmd+refresh on the calendar pane called `db.calendarEvents.clear()` outright. Now preserves `~`-id rows, mirroring how the email branch preserves snoozed threads.
  - Also: `createEvent` now passes `tempCompoundKey` as the `clientToken` the hub's `DedupStore` (`cal-create-dedup.json`, constructed in `index.ts` and passed to `handleCalendarRoutes`) already honoured — it was dead code because no client ever sent a token, so a retried create could double-book.
  - **Still open** (not loss paths, but they made the forensics impossible): `markDone` *deletes* queue rows, so a success leaves no audit trail, and `db.queue` has no `eventCompoundKey` index.

### Property search (`con map property`) — 3-portal house-hunt poller
Alerts Yousef the moment a matching house is listed, anywhere in the "where to move" search area. **The polygon comes from an agent map-layer** (e.g. `where-to-move/livable-zone`, our Valhalla drive-time isochrone union) — so the criteria we curate in the vault and the area we curate on the map are the same object the poller queries. **We own the criteria; the hub owns querying, display, polling and alerting.** One portal per country: `PORTAL_BY_COUNTRY = {UK: rightmove, DE: immoscout24, IT: immobiliare}`.
- **Hub** `server/src/property/`: `types.ts` (the portal-agnostic `Criteria`/`Listing`/`PortalClient` contract WE own), `geo.ts` (polyline encode + `simplifyToLatLng` + `ringsInCountry` — each portal wants the same polygon in a different wire format), one client per portal, `store.ts` (`PropertySearchStore` → `~/.config/console/property-searches.json`), `sync.ts` (`PropertySync`, **hourly**, 30 s deferred first tick, `running` guard — modelled on `FlightSync`), `waf-token.ts`.
- **Alert-storm guard**: a search's first poll only **seeds** (`seeded` flag + `seenIds`, cap 4000, oldest-evicted) and fires zero notifications; later polls alert only on ids not in `seenIds`. `store.update()` **clears both whenever `criteria`/`layer`/`country` change**, so editing a search re-seeds instead of alerting on hundreds of pre-existing listings.
- **Pins are just an agent map-layer** — `updateLayer()` upserts `property/<label-slug>-<id-suffix>` via `MapLayerStore`, so the SPA renders + toggles them with **zero client-side change** (`MapTab`'s `BUILTIN_SUBLAYERS` is only for location/geocaches/meetup; everything else flows through `layers-subscribe.ts`). Notifications go out via `PushServer` (one per fresh listing up to 5, else a summary), index deltas via `SyncBus`. Pins are drawn from `store.lastResults`, so **`RESULTS_LIMIT` (store) caps the map, not just the API payload** — keep it ≥ `MAX_PINS` (sync) or pins silently truncate.
- **`unsupported` + post-filter contract**: every client returns the criteria its portal *couldn't* express; `sync.postFilter()` re-applies **only those** locally. Never re-check a filter the portal already applied — listings that simply don't expose the field would get dropped.
- **Sparse-field filters belong in `unsupported`, not in the query.** A portal's server-side filter drops every listing that *omits* the field; ours keeps them. Rightmove reports a floor area on only **~49%** of rows, so `minSize`/`maxSize` are deliberately never sent — `minFloorArea` is declared unsupported and post-filtered. Same for plot area on UK/IT.
- **The criteria set is chosen in a canvas tab**, not by memorising flags: Console → Home → canvas → **"Property criteria"** (`~/.config/console/canvas/tabs/property-criteria/`). One unified criteria set (`Criteria` is portal-agnostic — a per-country panel is the wrong shape), every field tagged with per-country UK/DE/IT capability chips (server-filter / post-filter / implied / impossible), and fields the portals support but the hub doesn't send yet marked `todo`. It emits the JSON plus the three `con map property set` commands; UK prices convert via a GBP/EUR rate input.
- Routes `server/src/routes/property.ts`: `/property/{searches,searches/:id,searches/:id/run,count,listings}`. CLI `con map property {list,add,get,set,remove,run,count,listings}` (`cli/src/commands/map-property.ts`; second word = the Map tab). `set` only sends `criteria` when a criteria flag was actually passed — an empty object would wipe the filters and force a re-seed. Pure logic (polyline/simplify/ring selection, seed-vs-alert, `postFilter`) is unit-tested in `server/src/__tests__/property.test.ts`; live smoke test against the real sites via the compiled output: `~/sync/brain/root/projects/home/test-portal-clients.mjs [uk|de|it]`.
- **Protocol traps, all live-verified 2026-08-15** — full notes in `~/sync/brain/root/projects/home/{rightmove,immobiliare,immoscout24}-api.md`:
  - **All three portals fail OPEN on unknown params** (a typo'd filter is silently ignored, count unchanged). Always verify a new filter actually *moved* the count. IS24 alone hard-400s a bad *value* on a known enum.
  - **Rightmove needs both endpoints**: `/api/property-search/map/search` is clean JSON, 121 rows/page, but **ignores `sortType`**; `/property-for-sale/find.html` (`__NEXT_DATA__`, 24 rows/page) **honours `sortType=6`** = newest first. So `count()` uses the JSON one, `newest()` the HTML one. `index > 1000` → 400. `keywords` is a *sort*, not a filter → reported unsupported. Accumulate `resultCount` **once per ring** (`if (index === 0)`), not per page.
  - **immobiliare `/api-next/*` needs no auth or cookies.** `vrt=lat,lng;…` takes an arbitrary polygon. A cosmetic `path=` param is **mandatory** (omit → 500). Sort is **`criterio=data&ordine=desc`** — `criterioOrdinamento` fails open silently. `isResultsLimitReached` self-reports truncation. **It exposes no listing/creation date at all** — only an `isNew` boolean, so IT rows have `listedAt: undefined` and can't be locally sorted (the portal-side sort still delivers newest-first, so the seen-id diff is unaffected).
  - **ImmoScout24 has a split personality**: `POST /Suche/controller/search/{resultCountWithModel,change.go}` are cookie-free from plain fetch, but the `GET /Suche/shape/…` HTML holding the listings is **AWS-WAF gated (401)**. `waf-token.ts` drives a headless Chromium at the **homepage** (its first response IS the 401 challenge; it self-solves in ~3 s), harvests the `aws-waf-token` cookie (4-day TTL), and caches it 0600 for use from plain fetch. Playwright is **not a dependency** — resolved from other repos on this machine, absent → counts still work, listing reads degrade to an error.
  - **IS24 `&pagenumber=1` is a WAF 401.** `sorting=2` alone → 200, `sorting=2&pagenumber=2` → 200, `sorting=2&pagenumber=1` → 401. Page 1 must omit the param entirely.
  - **A WAF token can 401 days before its stated `expires`**, so TTL is not a validity test — only a real 401 is. `newest()` catches `WafRejected`, calls `WafTokenStore.invalidate()` (drops cache + file) and re-mints once before giving up. Without this a single early rejection silently killed DE results for the rest of the 4-day TTL.
  - **`change.go` compiles our query model into IS24's own short-param URL** (`price=-600000.0`, `ground=800.0-`, base64-swapped-alphabet `shape=…`) — never reverse-engineer that grammar, just POST the model and use the returned `url`.
  - **IS24 coords come from `mapMarkers`, not the listing**: `address.wgs84Coordinate` exists on only ~35% of rows (the rest hide the street address), but `resultlist.resultlist.mapMarkers.results` — shipped in the same response — covers **100%**, giving hidden-address listings an approximate point. Markers **group co-located listings**, so expand `groupedListings[].realEstateId` or you'll match a third of them. Prefer the exact address coord, fall back to the marker.
  - IS24 misc: `accept: application/json` is **mandatory** on the POSTs (else it replies ISO-8859-1 and umlauts corrupt a UTF-8 parse); `price.value: 0` means "Preis auf Anfrage", not free; `onlyWithGarden` is a **no-op** for `HOUSE_BUY` (688→688) — `lotSizeRange` is the real plot-size filter; `numberOfRooms` is *Zimmer* (all rooms), so it reads ~1 above bedrooms. It's the only portal that filters plot size (`lotSizeRange`) **and** broadband (`minimumInternetSpeed`).
  - **Tenure is asymmetric.** Rightmove `tenureTypes=FREEHOLD,SHARE_OF_FREEHOLD` (share-of-freehold is functionally freehold for us; `COMMONHOLD` returns 0 rows anywhere yet). immobiliare `tipoProprieta=1` = full ownership, which is what excludes *nuda proprietà* (seller keeps lifetime use) and *multiproprietà* — both look like bargains and aren't. **Germany has no filter at all**: Erbbaurecht is the analogue but IS24 exposes nothing, so `freeholdOnly` is simply unenforceable in DE (declared unsupported, and not post-filterable either since the listing doesn't carry it).
  - **Auctions and schemes are separate `Criteria` fields, `excludeAuctions` and `excludeSchemes`** — an auction isn't inherently undesirable (just a faster ~28-day cash-ready completion, no survey contingency), so it's a distinct opt-out from retirement/shared-ownership stock, not bundled with it. **Rightmove's `dontShow=auction` is behind a feature switch** and silently does nothing, so `excludeAuctions` is *always* declared unsupported on every portal and matched on listing text (`matchesAny()` in `sync.ts`, against `AUCTION_TERMS`); `excludeSchemes` uses `SCHEME_TERMS` and is a real Rightmove filter (`dontShow=retirement,sharedOwnership` + `includeSSTC=false`) but unsupported on DE/IT. immobiliare's `noAste` is the auction flag specifically — a real bug had it wired to `excludeSchemes` instead of `excludeAuctions` until 2026-08-15.
  - **`houseSubtypes` narrows `propertyType: 'house'`** to a portable subset (`detached | semi-detached | terraced | bungalow | villa | farmhouse | land`), mapped per portal — Rightmove `propertyTypes` (villa/farmhouse hard-400, no value exists), IS24 `houseTypes` enum (land has no `realEstateType` at all — `SITE_BUY`/`LAND`/`PLOT_BUY` all 400), immobiliare `idTipologia[]` (no bungalow or land id in the taxonomy). Requesting an unmappable subtype alone (e.g. `bungalow` on immobiliare) must fall back to the default house set, never to "no type filter" — an earlier version of the immobiliare client sent literally nothing in that case, silently widening the query to every residential type including flats.
  - **`numberOfRoomsRange` must be shifted by `ROOM_OFFSET = 1`** — IS24 counts *Zimmer* (all habitable rooms incl. the living room), so a 3-bed house is a 4-Zimmer-Haus. Feeding bedroom counts straight in makes every DE search a whole room stricter than the UK/IT one, invisibly.
  - **Because IS24 fails open on unknown fields, an invented field name is worse than an error** — it looks like a working filter and silently isn't. Never emit a query-model field that isn't in the api notes: bathrooms has no verified field, so `minBathrooms` is post-filtered on the listing's `numberOfBathRooms`.
  - Parse embedded JS object literals by **brace-matching**, never regex — `pageModel(html, marker)` is exported from `rightmove.ts` and reused for IS24's `resultListModel:`. (Related: regexing minified JS bundles catastrophically backtracks; use Python `re.finditer` + manual slicing.)
- **Etiquette**: personal-scale read-only research. Rightmove's own response embeds a `termsOfUse` reserving the API for Rightmove Group — keep request rates low, don't redistribute. Hourly is deliberate; don't tighten it. **Never persist portal session cookies** into the repo or the vault (the minted `aws-waf-token` cache under `~/.config/console/` is the one sanctioned exception).

### Google Maps search + directions (`con map gmaps`) — overlay, not a basemap swap
Goal: search Google Maps locations and overlay directions on the Map tab so it can replace day-to-day Google Maps use — **without** dropping the MapLibre+CARTO basemap (Google results are *overlaid*, tiles stay CARTO). On mobile the ask is narrower: find places + "Open in Google Maps" deep link for actual navigation (the phone already has the app).
- **Provider = Google Maps Platform** (Places API New + Routes API), one Cloud key. **The key never reaches the browser** — the hub proxies everything under `/gmaps/*` and the key is stored server-side in `auth.json` (`googleMaps.apiKey`, via `AuthStore.getGoogleMapsKey/setGoogleMapsKey/clearGoogleMaps`; status exposes `{configured}` only). Set it with `con map gmaps credentials --key <AIza…>` / clear with `--clear`, or the in-panel key form (shown when `gmapsConfigured === false`). The key must be a **real Maps Platform key (starts `AIza`)** — an OAuth2 token (`AQ.Ab8…`) 401s with "API keys are not supported by this API". Places API (New) **and** Routes API must be enabled in the Cloud project with billing on, or you get a 403 "has not been used in project … before or it is disabled".
- **Hub** `server/src/gmaps/client.ts` (`GoogleMapsClient`, ctor takes `AuthStore`): `searchText(query, bias?)` → `POST places:searchText` (text search, region-biased `gb`, viewport `locationBias` when a center is passed); `autocomplete(input, {lat,lon,radiusMeters,sessionToken})` → `POST places:autocomplete` (type-ahead); `placeDetails(placeId, sessionToken?)` → `GET places/{id}` (resolve a suggestion to a full place); `computeRoutes({origin,destination,travelMode,alternatives})` → `POST directions/v2:computeRoutes`. Field masks are explicit (`X-Goog-FieldMask`). Routes asks for `computeAlternativeRoutes:true` + `polylineEncoding:'GEO_JSON_LINESTRING'` so geometry drops straight onto MapLibre with no polyline decode; duration is a protobuf `"1234s"` string (`parseDurationSeconds`). **`routingPreference:'TRAFFIC_AWARE'` is DRIVE-only** — sending it for WALK/BICYCLE/TRANSIT 400s.
- **Autocomplete session tokens**: a `crypto.randomUUID()` token (module-level `_gmapsSession` in `src/store/map.ts`) is sent on every keystroke AND to the follow-up `placeDetails`, grouping them into ONE billable Google session; `resetGmapsSession()` rotates it after each details fetch. Client debounces 250 ms, guards `q.length < 2`, and drops stale responses (`if (get().gmapsQuery.trim() === q)`).
- **Routes** `server/src/routes/gmaps.ts`: `GET /gmaps/status`, `POST /gmaps/credentials`, `DELETE /gmaps/credentials`, `GET /gmaps/search?q=&lat=&lon=&radius=`, `GET /gmaps/autocomplete?q=&lat=&lon=&radius=&session=`, `GET /gmaps/place/:placeId?session=`, `POST /gmaps/directions {origin,destination,mode,alternatives}`. Wired in `index.ts` (`const googleMapsClient = new GoogleMapsClient(authStore)` + `if (path.startsWith('/gmaps') && handleGmapsRoutes(...))`). CLI `cli/src/commands/gmaps.ts` (`con map gmaps {status,credentials,search,directions}`; second word = the Map tab).
- **Client render**: search pins + routes are **ephemeral client-store sources** (`gmaps-pins`, `gmaps-routes` in `MapTab.tsx`), NOT persisted agent layers — like geocache/meetup pins. Store slice in `src/store/map.ts` (`gmapsConfigured/gmapsResults/gmapsSuggestions/gmapsRoutes/gmapsSelectedRoute/gmapsSelectedPlaceId` + `searchGmaps/autocompleteGmaps/pickSuggestion/selectPlace/getDirections/selectRoute/clearGmapsSearch`). UI is `GmapsPanel` (search box + type-ahead dropdown + results + directions with travel-mode toggle + route alternates) and `PlaceDetailPanel`, both with an "Open in Google Maps" deep link (`gmapsDirUrl`). The panel reads the map center via `mapController.center()` (added to `src/map/controller.ts`) — no map ref leaks into the panel.
- **WebGL crash containment**: `new maplibregl.Map()` throws *synchronously* ("Failed to initialize WebGL") when no GL context is available (hardware accel off, GPU blocklist). That throw is inside MapTab's init `useEffect` — uncaught it unwinds the **whole** React tree and blanks the entire app, not just the Map pane. It's wrapped in try/catch → a `glError` state renders a Map-pane-only "Map unavailable" message and the rest of Console keeps working. Diagnose a blank map with a `/debug/eval?target=chrome` canvas `getContext('webgl')` probe (`NO_CONTEXT` = WebGL disabled in the browser, not our bug).

- **Queued messages — "send when the WHOLE turn is done"** (`Session.queuedMessage` + `queueMessage`/`setQueuedMessage`/`flushQueuedMessage`/`flushIfIdle`). Distinct from **steering**: writing to the CLI's stdin mid-turn lands at its next *tool boundary*, so anything held client-side and released on a timer would interrupt the turn. The queue therefore lives **hub-side**, which also makes it survive a page reload, the phone backgrounding, and a hub restart mid-turn (`ManifestEntry.queuedMessage`, restored via `SessionOptions`). **ONE buffer that grows** (Yousef's call, not a FIFO): a second queue appends blank-line-separated and the whole thing arrives as a single prompt. **Four flush points, all needed**: (1) `handleResultMessage` — the normal turn end; (2) the **interrupt-resume branch of the `exit` handler**, which emits a *synthetic* `result` via `emitHub` and so bypasses `handleResultMessage` entirely (without this an interrupt strands the queued prompt until some later turn ends); (3) inside `queueMessage` via `flushIfIdle()` — queueing on an idle session is just sending; (4) the `index.ts` restore loop for a queue restored onto an *idle* session (`setTimeout(…, 1_000)`, matching the nudge delay). A `wasRunning` session needs none of these — its restart nudge re-runs the turn and flush (1) fires at its end. **Do NOT flush from the constructor** — it races the "hub was restarted, continue" nudge and converts the queued prompt back into steering. `flushQueuedMessage` clears the slot **before** `sendMessage` (which flips status to `running`) or a re-entrant flush double-sends; it logs the prompt so the transcript shows it. `kill()` drops the queue. The `session_queued` broadcast bypasses `emitHub` (which logs everything but `status`/`tool_input_delta`) via a direct `this.emit('hub_message', …)`, exactly like `scanForAttention` — it's ephemeral state, not transcript, and is deliberately absent from `LoggableHubMessage`; the authoritative value rides `SessionInfo.queuedMessage`. Hibernation needs no special case (`sendMessage` is already hibernation-aware, so a flush wakes the session). Surface: protocol `queue_message`/`set_queued_message` → `session_queued`; store `queueMessage`/`setQueuedMessage`; UI in `AgentPromptInput.tsx` — **Ctrl/Cmd+Enter** queues (falls through to a plain send with no active session; **Shift+Enter is now the only newline**), a `Clock` chip above the composer shows the pending text with click-to-edit (pulls it back into the textarea and clears the queue, so re-queueing replaces rather than doubles) and an X to cancel, and while running the button cluster is `[Square (interrupt), Send]` where the Send **tap steers now** and **long-press (500 ms) queues** — that's the mobile trigger (`longPressFired` swallows the click that follows a fired press).
- **Idle hibernation** (`Session.hibernate()` + sweep in `index.ts`, 5-min cadence). Every live `claude` subprocess holds ~250MB RSS even idle — ~48 parked sessions were 12GB. Sessions idle >30min get their subprocess SIGKILLed (`hibernating` flag → exit handler flips `hibernated`, status stays `idle`, messageLog/unread/claudeSessionId intact — NO `session_ended`); the next `sendMessage` transparently re-spawns with `--resume` (a message racing the SIGKILL is queued in `pendingWakeMessage` and delivered after wake). **Restore-into-hibernation**: the hub-restart restore loop passes `hibernateOnStart` for idle sessions (`!wasRunning`, Al exempt) so a restart spawns ~zero subprocesses instead of thundering 40+. ### Agent org chart — durable roles (`server/src/agents/registry.ts`)
Each agent is a **durable role** that outlives any live session, modelled on the Al pattern. State is an **agent-owned markdown file** `~/.config/console/agents/<key>.md`: frontmatter (`title`, `manager` = parent role's key, `goals`, `cwd`, `created`) + body (charter prose + a `## Memory` section the agent maintains). The **agent edits this file** with normal Read/Edit tools; the **hub reads it and never clobbers the body**.
- **`AgentRegistry`** (`server/src/agents/registry.ts`): boot-scans `agents/*.md` (parsed via the `yaml` dep — robust to comments/block-lists, unlike the hand-rolled `al/users.ts` parser), exposes `get/list/tree/resolveCharter/mintKey/create/setManager/delete`, and `fs.watch`es the dir (content-compared so the hub's own writes don't re-broadcast). `buildOrgTree()` is a pure, unit-tested fn that derives the org tree from `manager` edges and is defensive: a missing manager → annotated root (`danglingManager`), cycles broken with a visited-set (`cycleBroken`), nothing dropped.
- **Charter injection**: the role body becomes `--append-system-prompt` at the **`createSession` choke point** (`routes/agents.ts`) — only on a FRESH spawn (`!resume`, mirroring `session.ts`'s rule) and only when the caller didn't supply its own prompt (so Al keeps `buildAlSystemPrompt`). To apply an edited charter you must fresh-spawn — `con agent reload <name>` / the profile-panel "Reload" routes a role-backed session to `reloadAgentRole` (fresh spawn, charter re-derived; the `## Memory` carries forward). The **only field the hub writes is `manager`**, via a surgical single-line frontmatter stamp (`setManager` — never a `yaml.parse→stringify` round-trip, which would reorder keys / strip the agent's comments / reflow the body).
- **`agentKey`**: a stable, immutable slug (from the title), the join key across the role file ⇄ `ManifestEntry.agentKey` ⇄ `Session.agentKey` ⇄ `SessionInfo.agentKey`. Sessions resolve their role on spawn; a role with no live session is **parked** (revive = `reviveAgentRole` fresh-spawns it; ≤1 live session per role, enforced by a sweep mirroring the `delete_session` dup-guard).
- **Lifecycle**: `create_session{asAgent}` mints a role; `fork_session{seedRole}` mints a child role reporting to the source (`con agent chat` forks pass no `seedRole` → stay role-less). Ending a **durable** session **parks** the role (file stays — it's revivable); `delete_role` is the explicit removal (kills the live session + deletes the file; orphaned children become annotated roots, no cascade). **Al is the org root** (`agents/al.md`, `agentKey: 'al'`) but keeps its bespoke persona — `reload_session` special-cases `'al'` → `reloadAl`.
- **Fork roles are disposable, not parked** (`AgentRole.fork`, persisted as `fork: true` frontmatter; minted by `fork_session{seedRole}` via `create(..., {fork:true})`). A parked fork is pure org-chart clutter — nothing revives it — so when a fork session ends, `kill_session`/`delete_session` call `reapForkRole` → DELETE the fork role (durable roles still park). Guards: skipped if another live session still embodies the key (restart dup-guard); a fork-of-a-fork's children reparent up to the fork's manager first (no orphans). Legacy parked forks (created before this, no `fork:true`) are swept once on boot by the `.fork-cleanup-v1` marker migration in `index.ts`: dead `(fork)`-titled roles with no restorable session are deleted, surviving ones get `setForkFlag` stamped so they reap on their eventual end.
- **Backfill** (one-time, idempotent, in `index.ts` beside the fork-lineage backfill): turns every pre-existing named session into a role (title=name, manager=fork-parent's key via the shared `resolveParent`/`byName` two-pass, charter=initial prompt); writes only if the file is absent, stamps `agentKey` back to the manifest.
- **Surface**: protocol `agents_list{roles,tree}` (pushed on connect + every registry change) / `set_manager` / `revive_agent` / `get_agent_role` / `delete_role`; HTTP `GET/POST /agents/roles` (the out-of-band lever); CLI `con agent role list|get|manager|delete` + `con agent revive`.
- **UI** (`src/components/AgentTab.tsx`): a view-mode toggle (`agentViewMode`, localStorage `console:agents:viewMode`) flips the Agents pane between the session **list** and a visual **org chart** — `src/components/agent/AgentOrgChart.tsx`, a canvas node-link **tree** (`d3-hierarchy` `tree()` + `d3-zoom`, reusing the Notes circles-view canvas/zoom/drag engine; pure layout/hit-test in `agent-orgchart-helpers.ts`, unit-tested). **Folders are real role files** flagged `folder: true` (no session, drop targets, renamable). Interactions: left-click an agent → open its session, left-click a folder → its info; **right-click / long-press → context menu** (Show info, Open, Fork, Reload history/role, Revive, Rename, Delegate task…, Move to top level, Park, Delete — mirrors the list menu via a controlled `ContextMenuView`). Drag has a **6px threshold** so a jittery click isn't a reparent, and **drop-on-empty = cancel** (snap back), not make-root — drop on Al / "Move to top level" to go top-level. **Ctrl+Z / Ctrl+Y** undo/redo reparents + renames (store `orgPast`/`orgFuture`, scoped to the agents pane, ignored in inputs). A shared **"needs me" filter** (`filterAlerted`, store-backed) prunes the chart to the alerted subtree + ancestors. The role profile is a **modal** (`AgentInfoDialog` in AgentTab, opened via "Show info") not a bottom card; `AgentProfilePanel.tsx` shows charter/goals/`## Memory` (read-only — agent-owned) + a manager dropdown + revive/reload/park/delete (all guarded off for Al, the root).

### Board-driven delegation — vault kanban boards ARE the task store (`server/src/kanban/`)
The old `agent-tasks.json` delegation system (delegate/report RPC verbs, TasksPanel, `con agent delegate|report|tasks`) was **torn out 2026-08-14** and replaced: work assignment now lives in **plain-markdown Obsidian-Kanban boards in the vault** — human- and agent-editable with normal file tools, synced by Syncthing, no parallel store, no RPC.
- **Format** (`kanban/board.ts`, pure + lossless — round-trip verified byte-identical on all four real vault boards): Obsidian Kanban files (`kanban-plugin: board` frontmatter, `## Column` headings, `- [ ] card` lines, `%% kanban:settings` footer). Card grammar extensions are TRAILING tokens the plugin renders as harmless text: `@agentkey` = assignment, `^blockid` = Obsidian block-ref syntax, **stamped only by the hub at dispatch** — the id IS the dispatch marker (unstamped = not yet dispatched; deleting the id re-arms the card). Indented lines under a card are continuations (details). `parseCardTokens` requires tokens to be trailing so `alice@example.com` / `2^10` mid-text never match.
- **Dispatch** (`kanban/dispatch.ts` pure + `kanban/watcher.ts` `BoardWatcher`, wired in `index.ts`): the watcher polls the vault via `NoteStore.listSince` (mtime — same primitive as mobile notes sync; NOT fs.watch, the vault is written from every direction), classifies every changed `.md` (`isKanbanBoard`), and for each **assigned + unstamped + unchecked card under an In-Progress-like column** (`DISPATCH_COLUMN_RE`: in progress/doing/active/now): stamps a `^id` into the file, then wakes the assignee role's durable session (`reviveAgentRole` + `wakeSession`) with a self-instructing `[BOARD TASK]` envelope naming the board file. **Backlog is "planned", not "go"** — only dispatch columns trigger. All state is in the board files: a hub restart re-derives everything by re-reading boards (stamps prevent double-fires); a card assigned DURING an outage dispatches at next boot.
- **Completion is a file edit, not an RPC**: the agent moves its line under `## Done` (tick it) or `## Blocked` (+ an indented note). The watcher diffs in-flight (stamped) cards per poll and fires `onTransition` → broadcasts SyncBus `boards`/`transition` + wakes the assignee's **manager** (org edge, root = Al → relays to Yousef) with a `[BOARD UPDATE]`. Stale in-progress cards get nudged max 2× (`onStale`, 30-min steps).
- **Protocol preamble** (`agents/org-protocol.ts` `buildBoardProtocol()` — replaced `delegation-protocol.ts`): the hub-owned "how work flows" stanza appended to every role's `--append-system-prompt` at the `createSession` choke point and to Al's persona. `buildOrgPosition()`/`renderOrgRoster()`/`shortDescription()` (org roster + neighbours + self-identity, told not to skip levels) survived the migration unchanged.
- **Watchdog semantics**: nudges are per-card via the poll loop (no more separate 5-min `runTaskWatchdog` interval).
- **Fork branch-point seed**: a UI fork (`fork_session` with `seed:true`, set by the SPA `forkSession`) gets a `[FORK — branched from <parent>]` marker (`buildForkSeed` in `merge.ts`) so it knows where its own branch begins vs the inherited history — makes a later merge summary crisp. `con agent chat` forks pass no `seed` (they inject their own side-conversation seed). **GOTCHA (load-bearing): `claude --fork-session` emits NO `system` init — and so never hands the hub the forked `claudeSessionId` — until it receives a first message.** The seed is therefore sent **immediately** after the fork spawns, NOT on `session_init` (which would deadlock: silent fork → no message → no init → no csid → a dead, unusable fork — exactly the symptom when forking a large session). This is why `con agent chat` forks work (they message immediately) and why a `seed:false` UI fork would hang. Verified by spawning `claude --resume <csid> --fork-session` with vs. without stdin input.
- **Merge-back — fork OR org child** (`server/src/agents/merge.ts` pure builders + `mergeIntoParent`/`captureNextTurn` in `routes/agents.ts`; `mergeFork` is a back-compat alias): fold a child's knowledge into its parent instead of discarding it. The child self-summarises (`captureNextTurn` injects a merge-request and captures its next turn's text), the digest is injected into the parent, then the child is closed. A SUMMARY, not the transcript — keeps the parent's context clean. **Parent resolves two ways**: (a) **fork lineage** — `parentClaudeSessionId` → the live source session (`buildMergeRequest`, "you are a fork"); (b) **org manager edge** — the child role's `manager` → that role's live session, **revived if parked** so it can receive the digest (`buildChildMergeRequest`, "folding you into your manager"). For an org child the parent **absorbs the role too**: the child's own sub-reports reparent up to the parent, and the child's role file is deleted. `buildMergeEnvelope(name, summary, kind)` labels it fork vs agent. Guards: child must be idle; needs a fork-parent or a manager; no self-merge; if no summary is captured the child is left alive. **The parent also absorbs the child's live crons**: `mergeIntoParent` calls `ctx.reassignCron` (wired to `HubCronScheduler.reassignSession`) to re-key every ACTIVE (non-disabled) cron task from the child's `claudeSessionId` to the parent's before the child is killed — otherwise those tasks would orphan and auto-disable after 10 "session not found" misses. The Cron jobs keep running untouched (they close over the mutated task object); skip counters reset so the parent doesn't inherit the child's miss streak; disabled tasks stay dead. Timing: reassign runs eagerly when the parent's `claudeSessionId` is already set (always true for a fork parent, matched on it; usually for a live manager), else defers to the parent's next `session_init` (a freshly-revived parked manager — crons fire minutes apart, so the csid lands first). Tests in `server/src/__tests__/cron-reassign.test.ts`. Surface: protocol `merge_session`/`session_merged`; CLI `con agent merge <id|conv|name>` + `con agent chat --id <conv> --merge`; UI "Merge into parent" in the session list **and** org-chart context menu (shown for forks and any non-root org child). The reversible alternative to killing.
- **Hand-off**: Al emits `@handoff(<agentKey>)` (sentinel parsed by `server/src/handoff.ts`, mirrors `attention.ts`; scanned on finalized text in `session.ts`, emits `session_handoff`). The SPA shows an opt-in "Talk to X" banner (store `pendingHandoff` → `acceptHandoff`) + a "↩ Back to Al" control (`handoffReturnTo`); the raw sentinel is stripped from Al's displayed text. **WhatsApp/voice hand-off is out of scope** — Al relays there.
- **Removed surface** (do not re-add): protocol `delegate`/`report`/`cancel_task`/`tasks_list`/`tasks`; HTTP `/agents/tasks*`; CLI `con agent delegate|report|tasks`; SPA `TasksPanel.tsx`, org-chart task badges + animated delegation edges, `useAgentStore.tasks/delegate/cancelTask`; `agents/{tasks,delegation,delegation-protocol}.ts`; `~/.config/console/agent-tasks.json` (file left on disk, no longer read). Ephemeral `--ephemeral` workers went with it — parallel throwaway work is `con agent create` or a fork.
- Unit tests: `kanban.test.ts` (parser round-trip + mutations), `kanban-dispatch.test.ts` (dispatchable/in-flight/watcher incl. restart-no-double-fire), `merge-orch.test.ts` + `delegation-spawn.test.ts` (merge + charter-injection survivors).

### Hub-side agent cron (`/cron/*`)
Claude Code's built-in `/loop` / `CronCreate` is session-scoped and DOES NOT survive hub restarts under our SDK transport (`--input-format stream-json`) — empirically verified, matches Anthropic bugs [#40228](https://github.com/anthropics/claude-code/issues/40228) (`durable: true` doesn't persist) and [#40081](https://github.com/anthropics/claude-code/issues/40081) (sessions with cron tasks vanish from `/resume`). So the hub runs its own.
- **Scheduler**: `server/src/cron/scheduler.ts` (Croner + debounced JSON persist to `~/.config/console/agent-cron.json`). Tasks keyed by `claudeSessionId` (stable across restarts; hub session ids are rejected). Forks get a new claudeSessionId so they inherit zero tasks. Fires by mirroring the post-restart "Continue." nudge path: `broadcast(user_prompt) + session.logMessage + session.sendMessage`. Auto-disables a task after 10 consecutive misses (session not found / ended). One-shot tasks self-remove after firing. Croner `protect: true` prevents overlapping fires when Claude takes longer than the cron interval to respond.
- **Guard scripts (token-free polling)**: a task may carry an optional `guard` — a shell command run (via `bash -c` in the session's cwd, 60 s cap) at **every** trigger, BEFORE any agent wake. `fire()` is async: it runs the guard first and only proceeds to `sendMessage` when the guard **exits 0**; a non-zero exit is the normal "nothing to do" case — skipped silently, **no tokens spent**, task stays scheduled. The guard's stdout (trimmed, 4 KB cap) is appended to the wake prompt (`\n\n--- guard output (\`<cmd>\`) --- \n…`) so the agent knows *what* changed. This is how "wake only when X changed" works with zero cost between changes — e.g. a script that curls a URL, diffs against a saved copy, and `exit 0` only on change. **Guard skips do NOT count toward the 10-miss auto-disable budget** (a guard saying "no change" for months is working, not failing); only session-not-found/ended does. Guard stdout is transient (`guardOutput`, stripped from the persisted JSON); the guard command itself persists and survives restarts. Surface: `POST /cron {…, guard}`, CLI `con cron add … --guard "<cmd>"` or `--guard-file <path>`. `runOnce`/`con cron run` also evaluates the guard (a manual run of a guarded task only wakes if the guard passes).
- **Routes** (`server/src/routes/cron.ts`): `GET /cron[?session=…]`, `POST /cron`, `DELETE /cron/:id`, `POST /cron/:id/run`, `GET /cron/upcoming?n=N`, `GET /cron/ics-token` (returns `{token, publicUrl}`), `GET /cron.ics?token=…` (constant-time compare; 403 on bad token; `Cache-Control: max-age=300`).
- **ICS**: `server/src/cron/ics.ts` expands each task into discrete VEVENTs (next 50 firings, 30-day window) via `Croner.nextRun()` — avoids the lossy cron→RRULE conversion. UTC timestamps, RFC5545 line folding + escaping. Calendar clients re-fetch periodically.
- **CLI**: `con cron list/add/remove/run/upcoming/ics-url`. `--trigger` accepts a 5-field cron, ISO datetime, or `+30m`/`+2h`/`+1d` (CLI resolves relative to ISO). `--once` flips recurring=false (implied for ISO/relative).
- **SPA**: `src/components/agent/CronPill.tsx` (status-bar chip) + `CronPanel.tsx` (side panel: list, run-now/delete, recurring/one-shot create form with live validation, ICS subscription URL with copy). Backed by `src/store/cron.ts` (polled, no WS sync in v1).
- **Public exposure for GCal**: Caddy serves the ICS at `https://con.amar.io/public/cron.ics?token=…` (the `/public/*` namespace is in the auth allow-list). Legacy `/cron.ics` is Caddy-rewritten to the new path so existing GCal subscriptions keep working. `getPublicIcsBase()` returns `CONSOLE_PUBLIC_ORIGIN` (default `https://con.amar.io`). Token query string is the only auth — don't share it.

### Push-to-talk (PTT) — system-wide hold-to-talk → STT → mic owner
A hardware/hotkey hold-to-talk that streams mic → hub `/stt` (OpenAI realtime, `{type:'audio',data:b64}` → `{interim|final,text}`) and on release routes the transcript to the **mic owner** session. Owner model in `server/src/mic.ts` (`MicState`: `ownerSessionId` persisted to `mic-owner.json`, transient `hot`); routes in `server/src/routes/mic.ts` (`/mic/status|owner|hot|say|compose`); SyncBus `mic` service in `index.ts` broadcasts `state` (owner/hot) + `compose` (transient, NOT in the subscribe snapshot — and the SyncBus never replays missed events). Default owner = explicit-if-live-else-Al. CLI `con mic status|give|pass|release|say|ptt`. SPA mirror in `src/store/mic.ts` + the `MicButton` in `AgentTab`.
- **Two delivery modes**: `/mic/say` = inject + **auto-send** to the owner; `/mic/compose` = drop into the owner's composer **unsent** for review (`AgentPromptInput` reacts to `composeSeq`). A composed draft **lingers** in the textarea until sent/cleared — by design (it's a review draft), so an earlier foreground compose can still be sitting there later; it is NOT a duplicate of a backgrounded `say`.
- **Desktop** (Sway, out-of-repo dotfiles): `$direct+c`/`$remote+c` hold → `~/exec/con-ptt` → `parec --rate=24000 … --latency-msec=50` → `/stt` WS, live transcript in a `foot` popup (`/tmp/con-ptt.live`), routes to `/mic/compose` (review) on release; waybar `custom/ptt` indicator (`/tmp/con-ptt.hot`).
- **Phone** (APK v26+): the rugged phone's Custom-key **"Open Zello"** Easy-shuttle mode is the ONLY one that emits the firmware-level `com.zello.ptt.down/.up` broadcasts (Zello PTT API action strings — independent of any app). `PushService.pttReceiver` records on `.down` (AudioRecord VOICE_RECOGNITION 24kHz mono PCM16 → `/stt`), and on `.up` routes to `/mic/compose` if `MainActivity.foreground` else `/mic/say`. Needs FGS type `microphone` + RECORD_AUDIO. The native service requires the **apk bearer** (pair the APK) — see [Known Issues] + `memory/project_android_js_bridge_bind.md`.
- **Two STT models, deliberately NOT one constant** (`server/src/stt.ts`). The realtime endpoint (`wss://…/v1/realtime?intent=transcription`) and the batch endpoint (`POST /v1/audio/transcriptions`) reject each other's model ids, so they need separate constants — `STT_MODEL = 'gpt-realtime-whisper'` (streaming: PTT, dictation, glasses mic) and `STT_BATCH_MODEL = 'gpt-transcribe'` (whole-file: `/stt` upload endpoint + Al's WhatsApp voice notes). A test in `__tests__/stt.test.ts` pins `STT_BATCH_MODEL !== STT_MODEL` so a "consolidate these" refactor fails loudly. **`gpt-live-transcribe` was live-A/B-tested (2026-07-31) and REJECTED** — it connects and accepts the identical GA session config but transcribes measurably *worse* than `gpt-realtime-whisper`; adding `turn_detection: server_vad` for it then breaks the explicit `input_audio_buffer.commit` (`input_audio_buffer_commit_empty` — VAD already consumed the buffer). **When probing the realtime endpoint, stream at true realtime pace (4800-byte chunks / 100 ms at 24 kHz mono PCM16)** — faster starves the streaming decoder and garbles every model, invalidating the comparison.
- **A turn only ends because the CLIENT says so — `{type:'done'}` on mic release** (`server/src/index.ts` `/stt` handler; `STT_FLUSH_IDLE_MS` / `STT_DONE_TIMEOUT_MS` in `stt.ts`; fixed 2026-08-11 after "no text at all off mobile"). `gpt-realtime-whisper` **rejects `turn_detection`**, so nothing closes a turn on its own: it streams deltas lazily and the tail sits unemitted for 5–8 s. Every client used to close the socket the instant the mic was released, so the ending was discarded — short utterances lost their last words and brief ones produced **nothing at all**. (The relay *had* a `let commitInterval` declared with a "periodically commit" comment that was **never assigned** — so no commit was ever sent. Dead code that read as a working feature.) Two commit triggers now exist, and **neither is a wall-clock timer** — that distinction is load-bearing, since periodic commits chop mid-sentence and were vetoed for wrecking accuracy (`memory/feedback_stt_no_periodic_commits.md`): (1) **idle** — every `append` resets a `STT_FLUSH_IDLE_MS`=600 ms timer, so a commit only lands in a genuine gap; (2) **`{type:'done'}`** — commits immediately, then the relay holds the socket open until the `final` lands and **closes it itself** (capped by `STT_DONE_TIMEOUT_MS`=4 s so a stuck turn can't strand the mic UI). Measured commit→`final` ≈ 600–700 ms, which is why the old flat 600/700 ms client grace periods were racing it and losing.
  - **Four independent implementations, all of which must send `done` and wait** — a fix to one is a fix to none of the others: `src/hooks/useDictation.ts` (SPA + APK WebView), `android/.../core/Dictation.kt` (native composer mic), `android/.../PushService.kt` `pttUp()` (hardware PTT key), and the out-of-repo `~/exec/con-ptt-stream.mjs` (Sway desktop PTT — easiest to forget).
  - **The `final` carries the WHOLE turn, so it supersedes the accumulated deltas** — appending it duplicates the utterance. The two Kotlin paths and the desktop script now replace rather than append; the SPA instead *suppresses* the final when deltas already covered it (`sawDeltaRef`), and that flag must **not** be reset in the teardown path — the final arrives *after* `stop()`.

The standalone Al daemon (`~/proj/code/al/`) was retired 2026-06-09. Its WhatsApp + voice + persona runtime now lives in-process at `server/src/al/` and is owned by Console hub. ## Matrix recovery workflow (hub-side)
The old browser "Settings → recovery key" flow was dropped in the hub-centric migration. Hub-side replacements live in `server/src/matrix/backup-restore.ts` + `secret-storage.ts`, exposed as:
- `POST /matrix/keys/restore-from-recovery-key {recoveryKey}` — decodes an `EsU…` key; tries direct `BackupDecryptionKey` match first, then SSSS unlock. SSSS path iterates **every** keyId that encrypts `m.megolm_backup.v1` — users often have the current default SSSS key point somewhere new (e.g. `RII4BrO2Ox`) while the backup secret is still encrypted under the previous key (e.g. `bXFaNVGpGwtYSl7WxkfM2aznevIvcl3z`). Decrypts all sessions via `/room_keys/keys` and imports into OlmMachine (+ persists via `saveBackupDecryptionKey`).
- `POST /matrix/keys/restore-cross-signing {recoveryKey}` — decrypts the three cross-signing private secrets (`m.cross_signing.{master,self_signing,user_signing}`) from account_data, calls `importCrossSigningKeys` then `bootstrapCrossSigning(false)`, and explicitly sends the returned device-signature upload (bootstrap requests do NOT flow through `outgoingRequests()`). Required after any hub re-login — bridges reject Olm from uncross-signed devices. Beeper's current default SSSS key `RII4BrO2Ox` ships with **no `iv`/`mac` verification block**, so the helper skips `verifySsssKey` when those are absent and relies on the secret's own MAC to reject wrong keys.
- `POST /matrix/keys/import-local-backup` — force-imports the on-disk M0 key backup into the hub's current OlmMachine. Useful after hub migrates to a new deviceId and the legacy browser-exported keys never got merged.
- `POST /matrix/decrypt-event {roomId, eventId|event}` — fetches raw event from the homeserver (or takes it inline) and decrypts via the hub's OlmMachine. Used to resurrect "🔒 Encrypted message" placeholders that the browser persisted to IDB when the hub couldn't decrypt them at sync time.

Multiple rotations of the recovery key are fine — keep older keys handy because `tryKeyAgainstVersion` walks **all** backup versions and the SSSS loop walks **all** keyIds, so any historical key that unlocks any of them still restores. Beeper's recovery keys (`EsU…` prefix) are SSSS keys, not direct `BackupDecryptionKey` seeds. Cross-signing secrets are often encrypted under a **different** (newer) SSSS key than megolm backup — the two routes accept different recovery keys on the same account.

## Debugging (PRIMARY METHOD)

**Use the embedded debug agent, NOT browser DevTools or Chrome MCP tools.**

The app has a built-in debug agent (`src/debug-agent.ts`) that streams all console output, network requests, and errors to the hub in real-time. Claude Code observes via HTTP endpoints:

```bash
# See recent events (console logs, network requests, errors)
curl -sk https://localhost:9877/debug/log?n=30

# Filter for errors
curl -sk https://localhost:9877/debug/log?n=100 | jq '.[] | select(.cat=="error")'

# Filter for failed network requests
curl -sk https://localhost:9877/debug/log?n=100 | jq '.[] | select(.cat=="net" and .status >= 400)'

# Execute JS in the browser (replaces Chrome MCP javascript_tool)
# ALWAYS pass ?target=chrome — with the APK also connected, an untargeted eval
# can hit its native debug agent, which errors "unknown command" on any JS
# (looks like a syntax problem, is a routing problem).
curl -sk -X POST 'https://localhost:9877/debug/eval?target=chrome' -H 'Content-Type: application/json' -d '{"code":"document.title"}'

# Get Zustand store state
curl -sk https://localhost:9877/debug/state

# Check if debug agent is connected
curl -sk https://localhost:9877/debug/status
```

The debug agent:
- Captures from page load (imported first in `main.tsx`)
- Survives navigation (WebSocket auto-reconnects)
- Works across all tabs/devices (all stream to same hub)
- Logs to `~/.config/console/debug.log` (NDJSON, auto-rotated at 5K lines)
- `window.__console` (dev-only) exposes Zustand stores + Dexie db for browser console access
- **Eval-probe trap**: `import('/src/store/x.ts')` from `/debug/eval` can resolve a DIFFERENT module instance than the app's after HMR churn (empty-looking stores that aren't). Probe via `window.__console.stores` or the DOM, never a fresh dynamic import
- **Isolated SPA verification from a worktree (never Yousef's live tab)**: `npx vite --config vite.verify.config.ts --port 5174` serves the worktree's SPA with a Caddy-like `/hub` proxy to the live hub that injects the local `cli` bearer on HTTP + WS upgrades and strips `Origin` (the hub's WS Origin allow-list would 401 `localhost:5174`). Drive it with Playwright (resolve from `~/proj/code/astera-app/node_modules/playwright/index.mjs`, `ignoreHTTPSErrors`): `page.route('**/hub/auth/session', fulfil {authenticated:true})` opens `GatedBoot` (that probe is cookie-only — a bearer can't satisfy it), everything else is real hub data. Use `waitUntil:'load'` (WS/polling never reach `networkidle`); a fresh page's `import('/src/store/x.ts')` IS the app's instance (the trap above is HMR-churn only). Inject fake store state via `setState` to exercise UI branches the live hub can't produce yet — a live `refreshSpaces` may race and replace it, so set everything a branch needs in ONE `setState`. ## Key Patterns

### SPA reads a new hub field → optional-guard it, always
Vite HMR ships the SPA reader IMMEDIATELY; the hub writer only ships at Yousef's next restart. In that window the live hub serves payloads WITHOUT the new field, and an unguarded access (`d.tags.includes(…)`) crashes the whole React tree, not just one component ("screen goes dark"). Three whole-tree crashes from this class in one night (spaces store, blog store, drafts.tags — f46404a). Rule: any new field on a hub payload consumed by the SPA gets `?? []` / `?.` at the point of use, no exceptions.

### Prefs: a FAILED load must never look like a loaded one (^prim-lark, 2026-09-03)
`src/prefs.ts` is the hub-backed pref cache (`GET/PUT /config`); `isPrefsLoaded()` is the guard every automatic writer uses to avoid persisting a default over the user's real value. It used to `catch → cache = {} ` and set `loaded = true` **anyway**, so one timed-out `/config` (4 s — trivial to blow past on a busy or restarting hub) left every reader seeing DEFAULTS while every guard said "safe to persist". The next automatic write then pushed those defaults up. Signature: *"my settings keep resetting, and then the WRONG ones persist"* — for ANY pref. Diagnosed from `~/.config/console/debug.log`, which records request AND response bodies: `GET /config → status 0, dur 4000`, then 42 s later `PUT {calendar.visibleIds: [2 items]}` whose response proved the hub still held 9. Now: `initPrefs()` resolves only on a SUCCESSFUL load, retries with backoff (2/5/15/30/60 s), leaves `isPrefsLoaded()` false until one lands, and grafts newer local writes over a late-arriving hub copy (`localWrites`, the `auth-store` graft lesson). `prefsReady()` therefore never resolves while the hub is unreachable — callers already race their own timeout and must not write on that path.
- **Corollary for any pref derived from in-memory state**: a Zustand store is created at import time, BEFORE the pref cache is populated (App hydrates it a few ticks later), so a write derived from the store's own state in that window persists a set missing everything. `registerOverlaySource` now seeds from `persisted ∪ in-memory` so a register can only ever ADD (it used to shrink the user's calendar selection to just the overlay), and App's hydration unions live overlay ids instead of replacing the set.

### Auth
- **Hub-managed OAuth** — all tokens stored server-side in `~/.config/console/auth.json`. Frontend bootstraps via `GET /auth/token`. Sign-in opens hub's `/auth/google/start` in a popup.
- **Multi-account** — hub stores multiple Google accounts. Calendar sidebar can add accounts via OAuth flow. **Adding an ADDITIONAL account must pass `?add=1`** to `/auth/google/start` — that switches `prompt` from `consent` to `select_account consent`. Without it Google silently re-consents whichever account the browser is already signed into, so "Add calendar account" just re-links the existing account and the new one never appears. The plain sign-in path deliberately stays `consent` (no chooser).
- **Token refresh** — hub proactively refreshes tokens 5min before expiry. Frontend re-fetches from hub on 401.

### Offline Sync Queue
- **Shared queue** — `src/db/sync-queue.ts` provides `enqueue()`, `markDone()`, `markFailed()` for all services
- **Action types** — email (`archive`, `send`, etc.), chat (`chatSend`, `chatMarkRead`), calendar (`calCreate`, `calUpdate`, `calDelete`, `calRsvp`, `calReminder`, `calLocation`)
- **Pattern** — optimistic IDB write → `set()` for instant UI → `enqueue()` → background processor flushes within 500ms
- **Retry** — 3 retries before marking `failed`. Queue survives page reload.
- **Undo** — delete actions show 5-second undo toast. Undo removes from queue + restores IDB.

### Chat (Matrix)
- **Hub-owned room snapshot.** The canonical view of every joined room (name, isUnread, unreadCount, avatar, memberCount, tags, snoozedUntil, lastMessage*) lives server-side in `server/src/matrix/chat-rooms-store.ts` (a `SnapshotStore` wrapper from `server/src/snapshot-store.ts`). Every `/sync` delta computes the row via `server/src/matrix/room-state.ts` (port of the SPA's old `processJoinedRoom` logic) and the store broadcasts on the `chat-rooms` service. Browser-side `src/matrix/chat-rooms-subscribe.ts` mirrors snapshot + deltas straight into `db.chatRooms`. Replaces per-device derivation — "mark read on PC → phone sees it" works without local divergence. RPCs registered under `chat-rooms`: `snapshot`, `markRead`, `markUnread`, `snooze`. **Manual unread is durable** (`RoomState.manualUnread`): a user "mark unread" has no homeserver concept, so `computeRoomState` previously cleared it on any sync reporting `notification_count=0` — and the big catch-up `resume`/sync after a hub restart touches enough rooms to wipe *all* manual markers at once. The sticky flag forces `isUnread` true across recomputes and is cleared only by an explicit `markRead` (`setRoomRead`); genuine notif-backed unread was never affected.
- Direct REST API (no matrix-js-sdk). E2EE via OlmMachine WASM. Long-polling sync.
- Local echo with `~timestamp.random` IDs. Bridge detection (WhatsApp, LinkedIn, Slack).
- Pre-rendered room views. Pinned favourites grid. Edit/delete diffs via `diffWords`.
- **Send failures surface in the UI**: Beeper bridges emit `com.beeper.message_send_status` events referencing the original encrypted event. Browser-side `src/matrix/sync.ts` flips `sendFailed` on the local echo and fires a notification. SUCCESS status clears any prior fail marker. Root cause of FAIL_RETRIABLE is almost always the hub device not being cross-signed — run `POST /matrix/keys/restore-cross-signing` (see Matrix recovery workflow below).
- **Force-rotate Megolm**: `matrix.rotateRoomKey({roomId})` RPC (→ `HubMatrixCrypto.invalidateRoomKey`) throws away the outbound session so the next send re-keys from scratch. Useful when a bridge gets into a wedged state. Note: `invalidateGroupSession` only touches the in-memory session, so we pre-load by calling `shareRoomKey(roomId, [], …)` first — otherwise after a hub restart the persisted stale session stays live.
- **Resume semantics (gap recovery)**: the hub runs one /sync loop and broadcasts `matrix.delta` over SyncBus — fire-and-forget, no per-client buffer. Reconciliation uses Matrix's **native** resumable-sync primitive: the client persists `next_batch` from every ingested delta (in `meta` table under `matrix:lastBatch`), and hands it back to the hub via `matrix.resume({since})` RPC on any wake signal. Hub calls `/sync?since=<token>&timeout=0`, decrypts, returns the delta directly (point-to-point, not broadcast). Trigger points all converge on a single debounced `reconcile()` in `src/hooks/useSync.ts`: (1) `hubBus.onConnect`, (2) `document.visibilitychange → visible` (critical for APK — the WebView pauses while backgrounded so WS stays "up" from JS's perspective and onConnect never fires), (3) `window.online`. `bulkPut` on event_id makes re-ingestion idempotent, so racing live-delta + resume is safe. If the homeserver rejects the `since` (expired), hub falls back to initial sync and flags `isInitial` on the response. `processJoinedRoom` gates `lastMessageBody`/`lastMessageTime` behind `advancesPreview` (newest-by-timestamp > existing) so out-of-order resume ingestion can't roll a room preview back to an older message. **A resume batch can carry an event AND its relation in one pass** — any relation handler (`m.replace` edits, reactions) must patch the in-flight `messages` array first and only fall back to `db.chatMessages.update` (which silently no-ops on a not-yet-persisted row; the `bulkPut` at the end then stores the pre-relation state — the "edit reached phone but not desktop" bug, fixed e2466c6).
- **Limited-timeline backfill**: Matrix `/sync` caps each room's timeline at ~10 events and sets `limited: true` + `prev_batch` when more happened during the gap. The APK WebView gets paused while backgrounded — on resume, its `since` token is far behind and sync returns many truncated rooms, so without backfill the local cursor jumps past real messages. - **Remote-open into an ALREADY-OPEN tab — three separate traps, all live-verified 2026-08-04.** The whole point of the verb is driving a Console tab the user is *not* looking at, into a file that may *already* be a tab. Each of these silently produced a wrong result:
  1. **`requestAnimationFrame` does not fire in a backgrounded OR occluded tab** (`document.visibilityState` still reads `"visible"` when merely covered by another window — so a visibility check does NOT detect it). `NotesEditorCore` deferred `new EditorView(...)` to a bare rAF, so on such a tab the editor **never mounted at all**: the tab bar and status bar rendered, the store had the file, and `document.querySelectorAll('.cm-content').length === 0` forever. Now `mount()` races `requestAnimationFrame` against `setTimeout(…, 50)` with a `mounted` latch (the rAF deferral itself must stay — it's what stops vim's `BlockCursorPlugin` calling `coordsAt` pre-layout). The `updateListener`'s content-flush debounce was rAF too, which stranded typed text out of the store on the same tabs; also now `setTimeout`.
  2. **The store's `editorView` slot is global and was untagged.** `NotesEditorCore` is `key={activeFilePath}`-keyed → full remount per file, so mid-switch between two already-open tabs the slot still holds the **previous** file's view; dispatching an anchor position into it scrolls the wrong document (or throws when out of range). `setEditorView(view, path)` now also stores `editorViewPath`, and `waitForEditorView(path)` requires `editorViewPath === path`.
  3. **An already-open tab holds the content read when it was opened** — and the caller has usually *just written* the file, so the user gets shown a stale buffer and the anchor they added jumps nowhere. `reconcileWithDisk()` (`disk-review.ts`; was `refreshFromDisk` until ^spry-fox) re-reads via the adapter and, because the editor does NOT remount for a content change, **dispatches the new text into the live view** as well as updating the store (setting `content` AND `savedContent`, or the tab comes back spuriously dirty). A differing disk copy opens an inline REVIEW rather than replacing (dirty buffer included — the user's text is the review base) — never clobber unsaved edits.
- **Open tabs are hub-backed, not localStorage** (`notesOpenTabs` pref; `persistTabs`/`loadPersistedTabs`/`restoreTabs` in `src/store/notes.ts`). The open-tab set is work-in-progress *context* — losing it is real loss — so the hub pref is authoritative and localStorage is only an offline mirror, read when the hub is unreachable at boot. Four load-bearing guards, each of which was its own data-loss path: (1) `restoreTabs()` awaits **`prefsReady()`** (raced against a 4 s timeout for tests / an unreachable hub) — reading the pref cache before `initPrefs()` resolves yields the empty default, and the next `persistTabs()` would write that emptiness over the real value; (2) `persistTabs` **no-ops the hub write while `!isPrefsLoaded()`** for the same reason (the local mirror still updates, and the next write after prefs land syncs); (3) a module-level `restoring` latch suppresses the per-`openFile` writes during a restore, so a reload landing mid-restore can't truncate the pref to however many tabs had re-opened — one write at the end, which also drops paths that no longer exist; (4) **`reconnectVault()`'s hub-adapter branch needs its own `restoreTabs()` call** — it doesn't go through `loadVaultFiles()`, so before this a hub-adapter boot came up with zero tabs regardless of what was persisted.

  - `streamAmountForMonth(stream, 'YYYY-MM')` — handles cadence + compounding growth.

  - `detectRecurring(txns)` — clusters by (label, ±50p amount band), requires ≥3 occurrences across ≥3 months. Surfaced in CashflowView as "Detected recurring".
  - `findTransferCandidates(txns, overrides)` — opposite-sign equal-amount within 3 days; UI for confirmation pending.

### Meetup events subsystem (`server/src/meetup/`)

Why: the store prunes ended events, so without a refresh a one-off fetch starves to zero within days and the SPA calendar overlay unregisters on empty — the recurring "meetup calendar disappeared" bug (^keen-kite). Never fetched = never polls; 1–4 req/day vs the 800 budget. A fetch = 1–`maxPages` requests.

### Property search (`con map property`) — 3-portal house-hunt poller
Alerts Yousef the moment a matching house is listed, anywhere in the "where to move" search area. **The polygon comes from an agent map-layer** (e.g. `where-to-move/livable-zone`, our Valhalla drive-time isochrone union) — so the criteria we curate in the vault and the area we curate on the map are the same object the poller queries. **We own the criteria; the hub owns querying, display, polling and alerting.** One portal per country: `PORTAL_BY_COUNTRY = {UK: rightmove, DE: immoscout24, IT: immobiliare}`.
- **`--max-rings N` means the N *largest-by-area* rings, not "the first N" or "enough to cover the area."** `outerRings()` sorts every ring in the layer largest-first before `ringsInCountry()` filters to one country, then `sync.rings()` slices to `maxRings`. A multi-lobe isochrone union can have far more country-local rings than `maxRings` (seen 2026-08-15: `where-to-move/livable-zone` had 10 UK / 18 DE / 11 IT rings, all three searches were still capped at the old default of 3). Any ring past the cutoff — however large in absolute terms — is never queried, silently: no truncation flag, no log line, just fewer matches than the real isochrone would produce. **Set `--max-rings` to the country's real ring count** (compute via `ringsInCountry`, or just try a couple of values and confirm `count` stops changing) rather than leaving an old default in place.
- **Hub** `server/src/property/`: `types.ts` (the portal-agnostic `Criteria`/`Listing`/`PortalClient` contract WE own), `geo.ts` (polyline encode + `simplifyToLatLng` + `ringsInCountry` — each portal wants the same polygon in a different wire format), one client per portal, `store.ts` (`PropertySearchStore` → `~/.config/console/property-searches.json`), `sync.ts` (`PropertySync`, **hourly**, 30 s deferred first tick, `running` guard — modelled on `FlightSync`), `waf-token.ts`.
- **Alert-storm guard**: a search's first poll only **seeds** (`seeded` flag + `seenIds`, cap 4000, oldest-evicted) and fires zero notifications; later polls alert only on ids not in `seenIds`. `store.update()` **clears both whenever `criteria`/`layer`/`country` change**, so editing a search re-seeds instead of alerting on hundreds of pre-existing listings.
  - **That guard only fires on a change to the `PropertySearch` record itself — not on the *content* of a map layer it already points at.** Repainting the same `layer` slug with different geojson (e.g. correcting a bad polygon) never touches `patch.layer`, so `requeried` stays false and every listing newly in-scope reads as "genuinely new" against the stale `seenIds` — a real alert-storm risk. `PropertySync.reseed(id)` / `store.reseed(id)` exists specifically for this: clears `seeded`/`seenIds` without touching criteria/layer/country. `POST /property/searches/:id/reseed`, CLI `con map property reseed <id>`. **Always run this before the next poll whenever a map layer a live search references gets its geojson replaced**, or run it right after replacing the layer, before anything else touches the search.
- **Pins are just an agent map-layer** — `updateLayer()` upserts `property/<label-slug>-<id-suffix>` via `MapLayerStore`, so the SPA renders + toggles them with **near-zero client-side change** (`MapTab`'s `BUILTIN_SUBLAYERS` is only for location/geocaches/meetup; everything else flows through `layers-subscribe.ts`; the one exception is the "not interested" button in `LayerFeaturePanel`, which POSTs `/dismiss` directly — see below). Notifications go out via `PushServer` (one per fresh listing up to 5, else a summary), index deltas via `SyncBus`. Pins are drawn from `store.lastResults`, so **`RESULTS_LIMIT` (store) caps the map, not just the API payload** — keep it ≥ `MAX_PINS` (sync); both bumped 200→600 on 2026-08-15 so a backfill's results aren't immediately truncated back down.
- **`dismiss` is a separate persisted set from `seenIds`, on purpose.** `PropertySearch.dismissedIds` — hides a listing's pin permanently, survives future polls *and* criteria edits (unlike `seenIds`, which `store.update()` deliberately clears on a criteria/layer/country change). A dismissal is a judgment about the listing, not about whether today's query happens to match it. `sync.dismiss(id, listingId, dismissed?)` writes through the store then calls `updateLayer()` immediately — the pin vanishes on the spot, not on the next hourly tick. `POST /property/searches/:id/dismiss {listingId, dismissed?}`, CLI `con map property dismiss <id> <listingId> [--undo]`, SPA button in `LayerFeaturePanel` (only rendered when the layer's feature carries `listingId`/`searchId` — added to pin `properties` in `updateLayer()`, excluded from the panel's generic key→value rows via `PANEL_SPECIAL`).
- **`backfill` is `newest()` with a much bigger `limit`, nothing more** — each client already self-limits at its own real ceiling (Rightmove `index>1000`, IS24 `page>=50`, immobiliare `isResultsLimitReached`/`maxPages`), so passing `BACKFILL_LIMIT=5000` instead of the hourly `FETCH_LIMIT=50` just lets a client walk further before hitting a wall it already respects — no new pagination logic needed. The part that had to be careful: `PropertySearchStore.recordBackfill()` is a distinct code path from `recordPoll()` — it merges into `lastResults` (dedup by id, existing pins the backfill doesn't re-surface survive) and marks every touched id as seen, but **never computes or returns a `fresh` list**, so a backfill can never trigger a notification regardless of how many "new" ids it turns up. `POST /property/searches/:id/backfill`, CLI `con map property backfill <id>`.
- **Nearest-airport drive+transit time, computed once per genuinely-new listing** (`property/airport-distance.ts`). The isochrone that gates the search polygon is a boolean pass/fail with no number attached and no record of *which* airport; this answers the follow-up question for one specific listing that's about to be shown. `AIRPORTS_BY_COUNTRY` is a static per-country list curated from the vault's `manifest.json` (UK) / `fra-reachable.json` (DE/IT) — the exact airports whose isochrones were unioned into the search polygon, so "nearest of these" is the right question by construction, not a separate global airport lookup. Narrows to the 3 straight-line-closest airports first (free), then asks the Routes API for real DRIVE time on just those (a straight-line-nearest airport isn't always the fastest to actually reach — motorway layout, river crossings) and takes the minimum; TRANSIT is then queried for that one winning airport only. **Requires a configured Google Maps key** (`con map gmaps credentials`, plus the Routes API enabled on the GCP project — Places and Routes are separate toggles, a key working for search can still 403 on directions) — `attachAirportDistances()` no-ops silently if `gmaps.isConfigured()` is false, so distances just don't appear rather than erroring the poll.
  - **TRANSIT is schedule-dependent, so it's never queried for "now."** Google defaults `computeRoutes` to the current instant when no `departureTime` is given — for an hourly poller that's indistinguishable from a live 2am query with zero service. `nextWeekdayMorningUtc()` always resolves to the next weekday 09:00 UTC that's still in the future (rolls a Friday-evening or weekend "now" straight to Monday), giving a reproducible "typical commute-ish morning" figure instead of whatever the wall clock happened to be. `departureTime` is deliberately only ever sent on `TRANSIT` calls (DRIVE already models "now" via `TRAFFIC_AWARE`).
  - **Only computed for listings that get their own individual push** — `fresh.length > MAX_ALERTS` (the >5 summary-push path) skips the lookup entirely, since that path shows no single listing's detail to attach a distance to. Keeps the API-call volume tied to "how many listings did we actually show," not "how many listings exist."
  - Persisted onto `Listing.nearestAirport` via `PropertySearchStore.setNearestAirport()` — a **separate write path from `recordPoll()`**, called after the poll already landed, so the pin (drawn from `lastResults`) and a fresh push both carry the figure without re-running the whole poll. Surfaces in three places: the pin's `airport` popup field, the per-listing push body (`airportSuffix()`), and `Listing.nearestAirport` itself for anything reading the JSON directly.
- **`notifyLayer` — a push-noise filter, distinct from the search polygon.** UK/DE/IT-wide searches generate far more genuinely-new listings than Yousef wants buzzing his phone for; `PropertySearch.notifyLayer` narrows *notifications only* — `PropertySync.filterForNotify()` runs `pointInGeometry()` (`geo.ts`, dependency-free ray-casting; no turf in this repo) against every geometry in the resolved geofence before deciding whether/how to notify. Listings outside it are **still merged into `lastResults` and drawn on the map** by the normal poll path — nothing about search/display changes, only whether the phone buzzes. The `>MAX_ALERTS` summary-vs-per-listing split happens on the **filtered** count, not the raw fresh count, so a UK-wide batch of 18 fresh listings with only 2 inside the notify layer correctly sends 2 individual pushes rather than one noisy "18 new" summary. Unset (the default) notifies on everything, unchanged from before.
  - **Two resolution modes, `geometriesForNotify()`**: a bare `group/name` map-layer slug, or a raw geojson file path (`/…`, `~/…`, or ending `.json`/`.geojson`) read straight off disk. The path mode exists specifically so a one-off geofence (e.g. one airport's isochrone) doesn't have to be re-published as a visible Map-tab layer just to be usable here — **published a `where-to-move/lhr-catchment` layer for this first, then removed it** once Yousef flagged it as unwanted clutter overlapping the other where-to-move layers; the live UK search now points `notifyLayer` straight at the vault's pre-existing `data/iso/51.46775,-0.45477-60min-auto.geojson` (Heathrow's own isochrone from the airport-fetch pipeline, never re-fetched — same file the merged `livable-zone` union was built from) instead.
  - `POST/PATCH /property/searches[/…]` pass `notifyLayer` straight through (untyped JSON body → `store.update()`'s spread), CLI `--notify-layer <slug-or-path>` on `add`/`set` (`set ... --notify-layer none` clears it — sent as JSON `null`, since `undefined` is dropped by `JSON.stringify` and would never reach the server to clear anything).
- **`notify` + `notifyCriteria` — WHETHER and WHAT to push, beside `notifyLayer`'s WHERE (^snug-orca, 2026-09-03: "way too many house notifications — only UK, only when really good").** Both notification-only: polling, `lastResults` and map pins are untouched, and `store.update()` never re-seeds on them (only criteria/layer/country do). `notify: false` = poll + draw, never push — set on DE + IT so only the UK search buzzes. `notifyCriteria` (`server/src/property/notify-filter.ts`, pure + unit-tested) is a stricter gate evaluated on each fresh in-geofence listing: `maxPrice`, `minBedrooms`, `minPlotArea`, `minFloorArea`, `houseSubtypes` (matched against the listing's own `propertyType` text via `normaliseHouseType` — a semi never passes a gate that omits `semi-detached`, whatever else its text says; unclassifiable text fails), `keywords` (any-of over title/summary/address), `maxAirportDriveMinutes` (the one gate needing a lookup — `filterByAirportDrive` runs the Routes lookup on the survivors of everything else, capped at `DRIVE_GATE_MAX_LOOKUPS=10` per poll). **Strictness rule, opposite to `postFilter`: a field the listing omits FAILS the gate** — a push is a positive claim, unknown isn't evidence. Consequence: **Rightmove never exposes plot area** (0 of 516 live UK results carried one), so the search's own `minPlotArea: 800` is unenforced on UK (the feed is effectively "any ≤£300k freehold house", 71 % semis) and `notifyCriteria.minPlotArea` would silence the UK search outright. UK gate set to `houseSubtypes: [detached, bungalow, villa, farmhouse, land]` + `maxPrice: 250000` (~10 % of current UK matches pass). The summary-vs-per-listing split happens on the GATED count. CLI: `con map property set <id> --notify on|off`, `--notify-max-price/--notify-min-beds/--notify-min-plot/--notify-min-area/--notify-house-subtypes/--notify-keywords/--notify-max-drive` (any gate flag replaces the whole gate as one object), `--notify-criteria none` clears it. Also fixed on the way: `PropertySearchStore.create()` silently dropped `notifyLayer` (`add --notify-layer` never persisted; only `set` worked).
- **Mobile parity gap (fixed 2026-08-16): property pins/pushes were both dead ends on Android.** The APK is native (Kotlin/Compose, no WebView — see the Android section below), so a change made only in `MapTab.tsx` doesn't reach it; property pins render through Android's own `AgentFeaturePanel`/`agentFeatureInfo` in `MapScreen.kt`, a generic-agent-layer port that predates `listingId`/`searchId`/dismiss (the SPA's `PANEL_SPECIAL` + dismiss button were added *after* the Android parity build). Two separate fixes were needed, not one: (1) the panel now special-cases `url` as a tappable "open" button instead of an inert text row, and adds "not interested" (`MapRepository.dismissListing`) when both `listingId`+`searchId` are present; (2) the push notification tap fix lives in the push-notification note above (`PushMessage.url`). **When adding a property-specific (or any agent-layer-specific) UI feature, it needs both a SPA change AND an Android change — check `MapScreen.kt`/`MapRepository.kt`, not just `MapTab.tsx`.** Android-side fixes land in `android/BACKLOG.md` "Built, awaiting release" per the APK house rule — they don't ship until Yousef cuts a release.
- **`unsupported` + post-filter contract**: every client returns the criteria its portal *couldn't* express; `sync.postFilter()` re-applies **only those** locally. Never re-check a filter the portal already applied — listings that simply don't expose the field would get dropped.
- **One bad ring silently kills the whole poll.** `pollSearch()` wraps the entire per-search fetch in a single try/catch — a thrown error from ring 4 of 18 means rings 1–3's results are discarded too, `lastTotal`/pins stay stale, and the only trace is a one-line hub log (`pm2 logs console-server`), nothing user-visible. Two real instances found 2026-08-15, both from treating "each ring is independent" as true when the *loop* isn't fault-isolated per ring:
  - **IS24: XML→JSON singleton flattening.** A results page with exactly one hit collapses `resultlistEntry` from an array to a bare object (same class of bug as `galleryAttachments.attachment`) — `for...of` on it throws `entries is not iterable`. Fixed by `asEntryArray()` in `immoscout24.ts`, normalising array-or-object to an array. Any newly-added field that's "usually an array" in this API needs the same guard, on principle.
  - **immobiliare: `vrt` 422s under 4 vertices.** A ring whose raw coords include a duplicated closing point can Douglas-Peucker down to a 3-point sliver (~15m triangle, a real union artifact near Trieste) — immobiliare rejects it with `"This collection should contain 4 elements or more"`. Fixed by `isTooSmall()` in `immobiliare.ts`, skipping (not erroring on) any ring below `MIN_VERTICES = 4` after simplification.
  - Neither bug was cheap to find: `count()` uses fresh per-ring requests same as `newest()`, so `con map property count` kept reporting a correct, larger total while `run`/the hourly poller silently produced the old, smaller one — the discrepancy between the two was the tell. **If a search's `lastTotal` doesn't move after a criteria/maxRings edit despite a matching `count` call showing a different number, suspect a ring-loop crash before anything else — check `pm2 logs console-server | grep property-sync`.**
- **Sparse-field filters belong in `unsupported`, not in the query.** A portal's server-side filter drops every listing that *omits* the field; ours keeps them. Rightmove reports a floor area on only **~49%** of rows, so `minSize`/`maxSize` are deliberately never sent — `minFloorArea` is declared unsupported and post-filtered. Same for plot area on UK/IT.
- **The criteria set is chosen in a canvas tab**, not by memorising flags: Console → Home → canvas → **"Property criteria"** (`~/.config/console/canvas/tabs/property-criteria/`). One unified criteria set (`Criteria` is portal-agnostic — a per-country panel is the wrong shape), every field tagged with per-country UK/DE/IT capability chips (server-filter / post-filter / implied / impossible), and fields the portals support but the hub doesn't send yet marked `todo`. It emits the JSON plus the three `con map property set` commands; UK prices convert via a GBP/EUR rate input.
- Routes `server/src/routes/property.ts`: `/property/{searches,searches/:id,searches/:id/run,count,listings}`. CLI `con map property {list,add,get,set,remove,run,count,listings}` (`cli/src/commands/map-property.ts`; second word = the Map tab). `set` only sends `criteria` when a criteria flag was actually passed — an empty object would wipe the filters and force a re-seed. Pure logic (polyline/simplify/ring selection, seed-vs-alert, `postFilter`) is unit-tested in `server/src/__tests__/property.test.ts`; live smoke test against the real sites via the compiled output: `~/sync/brain/root/projects/home/test-portal-clients.mjs [uk|de|it]`.
- **Protocol traps, all live-verified 2026-08-15** — full notes in `~/sync/brain/root/projects/home/{rightmove,immobiliare,immoscout24}-api.md`:
  - **All three portals fail OPEN on unknown params** (a typo'd filter is silently ignored, count unchanged). Always verify a new filter actually *moved* the count. IS24 alone hard-400s a bad *value* on a known enum.
  - **Rightmove needs both endpoints**: `/api/property-search/map/search` is clean JSON, 121 rows/page, but **ignores `sortType`**; `/property-for-sale/find.html` (`__NEXT_DATA__`, 24 rows/page) **honours `sortType=6`** = newest first. So `count()` uses the JSON one, `newest()` the HTML one. `index > 1000` → 400. `keywords` is a *sort*, not a filter → reported unsupported. Accumulate `resultCount` **once per ring** (`if (index === 0)`), not per page.
  - **immobiliare `/api-next/*` needs no auth or cookies.** `vrt=lat,lng;…` takes an arbitrary polygon. A cosmetic `path=` param is **mandatory** (omit → 500). Sort is **`criterio=data&ordine=desc`** — `criterioOrdinamento` fails open silently. `isResultsLimitReached` self-reports truncation. **It exposes no listing/creation date at all** — only an `isNew` boolean, so IT rows have `listedAt: undefined` and can't be locally sorted (the portal-side sort still delivers newest-first, so the seen-id diff is unaffected).
  - **ImmoScout24 has a split personality**: `POST /Suche/controller/search/{resultCountWithModel,change.go}` are cookie-free from plain fetch, but the `GET /Suche/shape/…` HTML holding the listings is **AWS-WAF gated (401)**. `waf-token.ts` drives a headless Chromium at the **homepage** (its first response IS the 401 challenge; it self-solves in ~3 s), harvests the `aws-waf-token` cookie (4-day TTL), and caches it 0600 for use from plain fetch. Playwright is **not a dependency** — resolved from other repos on this machine, absent → counts still work, listing reads degrade to an error.
  - **IS24 `&pagenumber=1` is a WAF 401.** `sorting=2` alone → 200, `sorting=2&pagenumber=2` → 200, `sorting=2&pagenumber=1` → 401. Page 1 must omit the param entirely.
  - **A WAF token can 401 days before its stated `expires`**, so TTL is not a validity test — only a real 401 is. `newest()` catches `WafRejected`, calls `WafTokenStore.invalidate()` (drops cache + file) and re-mints once before giving up. Without this a single early rejection silently killed DE results for the rest of the 4-day TTL.
  - **`change.go` compiles our query model into IS24's own short-param URL** (`price=-600000.0`, `ground=800.0-`, base64-swapped-alphabet `shape=…`) — never reverse-engineer that grammar, just POST the model and use the returned `url`.
  - **IS24 coords come from `mapMarkers`, not the listing**: `address.wgs84Coordinate` exists on only ~35% of rows (the rest hide the street address), but `resultlist.resultlist.mapMarkers.results` — shipped in the same response — covers **100%**, giving hidden-address listings an approximate point. Markers **group co-located listings**, so expand `groupedListings[].realEstateId` or you'll match a third of them. Prefer the exact address coord, fall back to the marker.
  - IS24 misc: `accept: application/json` is **mandatory** on the POSTs (else it replies ISO-8859-1 and umlauts corrupt a UTF-8 parse); `price.value: 0` means "Preis auf Anfrage", not free — **confirmed live 2026-08-15** by fetching a flagged listing's own expose page and finding `<span class="is24-preis-value">Auf Anfrage</span>`, not a data error; `onlyWithGarden` is a **no-op** for `HOUSE_BUY` (688→688) — `lotSizeRange` is the real plot-size filter; `numberOfRooms` is *Zimmer* (all rooms), so it reads ~1 above bedrooms. It's the only portal that filters plot size (`lotSizeRange`) **and** broadband (`minimumInternetSpeed`).
  - **`excludePriceOnRequest` drops any listing with no price at all** — real signal, not noise: one DE poll had **37.5%** price-on-request. Genuinely unfilterable server-side on any of the three portals (no query param anywhere expresses it), so it's always post-filtered on `Listing.price == null`.
  - **Tenure is asymmetric.** Rightmove `tenureTypes=FREEHOLD,SHARE_OF_FREEHOLD` (share-of-freehold is functionally freehold for us; `COMMONHOLD` returns 0 rows anywhere yet). immobiliare `tipoProprieta=1` = full ownership, which is what excludes *nuda proprietà* (seller keeps lifetime use) and *multiproprietà* — both look like bargains and aren't. **Germany has no filter at all**: Erbbaurecht is the analogue but IS24 exposes nothing, so `freeholdOnly` is simply unenforceable in DE (declared unsupported, and not post-filterable either since the listing doesn't carry it).
  - **Auctions and schemes are separate `Criteria` fields, `excludeAuctions` and `excludeSchemes`** — an auction isn't inherently undesirable (just a faster ~28-day cash-ready completion, no survey contingency), so it's a distinct opt-out from retirement/shared-ownership stock, not bundled with it. **Rightmove's `dontShow=auction` is behind a feature switch** and silently does nothing, so `excludeAuctions` is *always* declared unsupported on every portal and matched on listing text (`matchesAny()` in `sync.ts`, against `AUCTION_TERMS`); `excludeSchemes` uses `SCHEME_TERMS` and is a real Rightmove filter (`dontShow=retirement,sharedOwnership` + `includeSSTC=false`) but unsupported on DE/IT. immobiliare's `noAste` is the auction flag specifically — a real bug had it wired to `excludeSchemes` instead of `excludeAuctions` until 2026-08-15.
  - **`houseSubtypes` narrows `propertyType: 'house'`** to a portable subset (`detached | semi-detached | terraced | bungalow | villa | farmhouse | land`), mapped per portal — Rightmove `propertyTypes` (villa/farmhouse hard-400, no value exists), IS24 `houseTypes` enum (land has no `realEstateType` at all — `SITE_BUY`/`LAND`/`PLOT_BUY` all 400), immobiliare `idTipologia[]` (no bungalow or land id in the taxonomy). Requesting an unmappable subtype alone (e.g. `bungalow` on immobiliare) must fall back to the default house set, never to "no type filter" — an earlier version of the immobiliare client sent literally nothing in that case, silently widening the query to every residential type including flats.
  - **`numberOfRoomsRange` must be shifted by `ROOM_OFFSET = 1`** — IS24 counts *Zimmer* (all habitable rooms incl. the living room), so a 3-bed house is a 4-Zimmer-Haus. Feeding bedroom counts straight in makes every DE search a whole room stricter than the UK/IT one, invisibly.
  - **Because IS24 fails open on unknown fields, an invented field name is worse than an error** — it looks like a working filter and silently isn't. Never emit a query-model field that isn't in the api notes: bathrooms has no verified field, so `minBathrooms` is post-filtered on the listing's `numberOfBathRooms`.
  - Parse embedded JS object literals by **brace-matching**, never regex — `pageModel(html, marker)` is exported from `rightmove.ts` and reused for IS24's `resultListModel:`. (Related: regexing minified JS bundles catastrophically backtracks; use Python `re.finditer` + manual slicing.)
- **Etiquette**: personal-scale read-only research. Rightmove's own response embeds a `termsOfUse` reserving the API for Rightmove Group — keep request rates low, don't redistribute. Hourly is deliberate; don't tighten it. **Never persist portal session cookies** into the repo or the vault (the minted `aws-waf-token` cache under `~/.config/console/` is the one sanctioned exception).

### Google Maps search + directions (`con map gmaps`) — overlay, not a basemap swap
Goal: search Google Maps locations and overlay directions on the Map tab so it can replace day-to-day Google Maps use — **without** dropping the MapLibre+OpenFreeMap basemap (Google results are *overlaid*, tiles stay OFM). On mobile the ask is narrower: find places + "Open in Google Maps" deep link for actual navigation (the phone already has the app).
- **Provider = Google Maps Platform** (Places API New + Routes API), one Cloud key. **The key never reaches the browser** — the hub proxies everything under `/gmaps/*` and the key is stored server-side in `auth.json` (`googleMaps.apiKey`, via `AuthStore.getGoogleMapsKey/setGoogleMapsKey/clearGoogleMaps`; status exposes `{configured}` only). Set it with `con map gmaps credentials --key <AIza…>` / clear with `--clear`, or the in-panel key form (shown when `gmapsConfigured === false`). The key must be a **real Maps Platform key (starts `AIza`)** — an OAuth2 token (`AQ.Ab8…`) 401s with "API keys are not supported by this API". Places API (New) **and** Routes API must be enabled in the Cloud project with billing on, or you get a 403 "has not been used in project … before or it is disabled".
- **Hub** `server/src/gmaps/client.ts` (`GoogleMapsClient`, ctor takes `AuthStore`): `searchText(query, bias?)` → `POST places:searchText` (text search, region-biased `gb`, viewport `locationBias` when a center is passed); `autocomplete(input, {lat,lon,radiusMeters,sessionToken})` → `POST places:autocomplete` (type-ahead); `placeDetails(placeId, sessionToken?)` → `GET places/{id}` (resolve a suggestion to a full place); `computeRoutes({origin,destination,travelMode,alternatives,departureTime?})` → `POST directions/v2:computeRoutes`. Field masks are explicit (`X-Goog-FieldMask`). Routes asks for `computeAlternativeRoutes:true` + `polylineEncoding:'GEO_JSON_LINESTRING'` so geometry drops straight onto MapLibre with no polyline decode; duration is a protobuf `"1234s"` string (`parseDurationSeconds`). **`routingPreference:'TRAFFIC_AWARE'` is DRIVE-only** — sending it for WALK/BICYCLE/TRANSIT 400s. **`departureTime` (RFC3339 UTC) is only ever sent for TRANSIT** — it's the only mode whose result is schedule-dependent; verified live that a fixed timestamp genuinely shifts the returned duration vs the implicit "now" default (property/airport-distance.ts's `nextWeekdayMorningUtc()` is the one caller that sets it, to avoid a poller landing on a dead-of-night query).
- **Autocomplete session tokens**: a `crypto.randomUUID()` token (module-level `_gmapsSession` in `src/store/map.ts`) is sent on every keystroke AND to the follow-up `placeDetails`, grouping them into ONE billable Google session; `resetGmapsSession()` rotates it after each details fetch. Client debounces 250 ms, guards `q.length < 2`, and drops stale responses (`if (get().gmapsQuery.trim() === q)`).
- **Routes** `server/src/routes/gmaps.ts`: `GET /gmaps/status`, `POST /gmaps/credentials`, `DELETE /gmaps/credentials`, `GET /gmaps/search?q=&lat=&lon=&radius=`, `GET /gmaps/autocomplete?q=&lat=&lon=&radius=&session=`, `GET /gmaps/place/:placeId?session=`, `POST /gmaps/directions {origin,destination,mode,alternatives,departureTime?}`. Wired in `index.ts` (`const googleMapsClient = new GoogleMapsClient(authStore)` + `if (path.startsWith('/gmaps') && handleGmapsRoutes(...))`). CLI `cli/src/commands/gmaps.ts` (`con map gmaps {status,credentials,search,directions}`; `directions` takes `--departure <RFC3339>`; second word = the Map tab).
- **Client render**: search pins + routes are **ephemeral client-store sources** (`gmaps-pins`, `gmaps-routes` in `MapTab.tsx`), NOT persisted agent layers — like geocache/meetup pins. Store slice in `src/store/map.ts` (`gmapsConfigured/gmapsResults/gmapsSuggestions/gmapsRoutes/gmapsSelectedRoute/gmapsSelectedPlaceId` + `searchGmaps/autocompleteGmaps/pickSuggestion/selectPlace/getDirections/selectRoute/clearGmapsSearch`). UI is `GmapsPanel` (search box + type-ahead dropdown + results + directions with travel-mode toggle + route alternates) and `PlaceDetailPanel`, both with an "Open in Google Maps" deep link (`gmapsDirUrl`). The panel reads the map center via `mapController.center()` (added to `src/map/controller.ts`) — no map ref leaks into the panel.
- **WebGL crash containment**: `new maplibregl.Map()` throws *synchronously* ("Failed to initialize WebGL") when no GL context is available (hardware accel off, GPU blocklist). That throw is inside MapTab's init `useEffect` — uncaught it unwinds the **whole** React tree and blanks the entire app, not just the Map pane. It's wrapped in try/catch → a `glError` state renders a Map-pane-only "Map unavailable" message and the rest of Console keeps working. Diagnose a blank map with a `/debug/eval?target=chrome` canvas `getContext('webgl')` probe (`NO_CONTEXT` = WebGL disabled in the browser, not our bug).

User prompts are never scanned (self-ping protection). Sets `Session.needsAttention = { ts, snippet }`, emits a `session_attention` hub message.

The `push: boolean` on the `session_attention` message is a transport-only hint; `routes/agents.ts` strips it before broadcasting and only fires `ctx.notifyAttention` (→ `pushServer`) when true. `clearAttentionPush` cancels the phone notification on clear.

Clients only do the optimistic local half.
- Al (personal AI) connects on `/al` WebSocket path.
- **Agent-to-agent forks** (`con agent chat`). Spawns a fork of a named session, injects a message, waits for the reply, prints `conv: <claudeSessionId>` then the reply text. Follow-up turns: `con agent chat --id <conv-id> "<message>"` routes via the fork's claudeSessionId (survives hub restarts). The fork is a real hub session — visible in `con agent list`, tailable, appears in the SPA sidebar (nested under the parent with a `GitBranch` glyph from `AgentTab`). The target's MAIN session is untouched. Implementation: `cli/src/commands/agent.ts` + `cli/src/ws-client.ts` (`streamWithSends`, `injectAndCapture`).
- **`--end` marks the fork ended (readable), doesn't delete it.** `con agent chat --id <conv-id> --end` sends `kill_session`: it terminates the fork's subprocess and sets `status: ended` but **keeps the entry in `con agent list`** so the conversation stays readable (Yousef's call — no auto-reap). To fully remove a fork from the list, `con agent kill <session-id>` (`delete_session`). The old bug — `--end` leaving a running `<name> (fork)` (caught 2026-06-09; re-reported by the personal-migration agent) — was a **duplicate** hub session sharing the fork's `claudeSessionId` (a resume during a restart spawns one): `kill_session` killed only the resolved session, leaving the dup running, while `con agent kill`'s `delete_session` dup-guard cleared all. Fixed by giving `kill_session` the same dup-guard (mark all matching `claudeSessionId` ended, kept in list) + a `sessions_list` broadcast, and making `Session.kill()` set `status:ended` unconditionally (not only when a live process exists).
- **Manifest** (`~/.claude/console-hub-sessions.json`, written by `server/src/manifest.ts`): the list the hub uses to re-spawn sessions at startup. Every write is **synchronous and atomic** (`writeFileSync` to a `.tmp` sibling, then `renameSync`) — no in-memory debounce buffer, so a SIGKILL or host crash can't lose pending state. Every session with a `claudeSessionId` is persisted regardless of `status` (yes, including `ended`); removal is driven only by `delete_session`, not by subprocess lifecycle. This prevents the old failure mode where SDK timeouts / process exits would silently prune sessions from the manifest, so a later restart would resume zero. If you ever need to manually rebuild the manifest from JSONL transcripts on disk: the hub clobbers external writes within ms of any session event, so the only reliable path is **write the new manifest then `SIGKILL` the hub in the same Node tick** (the shutdown handler also calls `saveManifest`, so SIGTERM would still clobber); pm2/tsx will respawn the hub and it'll load the new manifest cleanly. **SIGKILL the node process actually holding :9877 (`ss -tlnp`), NOT the pm2 wrapper pid** — killing the wrapper leaves the old hub serving while pm2's respawns crash-loop on EADDRINUSE, and one old-hub save wipes the edit (this exact miss reverted the 2026-08-26 binding backfill once; the tell was a removed route still returning 200).

### Hub-side agent cron (`/cron/*`)
Claude Code's built-in `/loop` / `CronCreate` is session-scoped and DOES NOT survive hub restarts under our SDK transport (`--input-format stream-json`) — empirically verified, matches Anthropic bugs [#40228](https://github.com/anthropics/claude-code/issues/40228) (`durable: true` doesn't persist) and [#40081](https://github.com/anthropics/claude-code/issues/40081) (sessions with cron tasks vanish from `/resume`). So the hub runs its own.
- **Scheduler**: `server/src/cron/scheduler.ts` (Croner + debounced JSON persist to `~/.config/console/agent-cron.json`). Tasks keyed by `claudeSessionId` (stable across restarts; hub session ids are rejected). Forks get a new claudeSessionId so they inherit zero tasks. **A csid is stable across hub restarts, hibernation wakes, `con agent reload <session>`, model/backend respawns — all `--resume`. Exactly two paths mint a NEW csid for an existing session, and both now re-key that session's active crons via `reassignSession` (^hazy-ram, 2026-09-02): (1) `con agent reload AL` (fresh persona spawn by design — `reloadAlSession` captures the old csid and re-keys on the new `session_init`); (2) the pruned-transcript fresh respawn (`session_init` carries `rekeyedFrom` when a pre-set resume csid differs from what the CLI minted; the `hub_message` listener in `routes/agents.ts` re-keys). Before this, Al's mail/yoga/grocery crons died on every persona reload (10 "session not found" misses → auto-disable) — Al lost a watched reply on 2026-09-02. Al's own AL.md boot-time rebind check is belt-and-braces, not the fix.** Fires by mirroring the post-restart "Continue." nudge path: `broadcast(user_prompt) + session.logMessage + session.sendMessage`. Auto-disables a task after 10 consecutive misses (session not found / ended). One-shot tasks self-remove after firing. Croner `protect: true` prevents overlapping fires when Claude takes longer than the cron interval to respond.
- **Guard scripts (token-free polling)**: a task may carry an optional `guard` — a shell command run (via `bash -c` in the session's cwd, 60 s cap) at **every** trigger, BEFORE any agent wake. `fire()` is async: it runs the guard first and only proceeds to `sendMessage` when the guard **exits 0**; a non-zero exit is the normal "nothing to do" case — skipped silently, **no tokens spent**, task stays scheduled. The guard's stdout (trimmed, 4 KB cap) is appended to the wake prompt (`\n\n--- guard output (\`<cmd>\`) --- \n…`) so the agent knows *what* changed. This is how "wake only when X changed" works with zero cost between changes — e.g. a script that curls a URL, diffs against a saved copy, and `exit 0` only on change. **Guard skips do NOT count toward the 10-miss auto-disable budget** (a guard saying "no change" for months is working, not failing); only session-not-found/ended does. Guard stdout is transient (`guardOutput`, stripped from the persisted JSON); the guard command itself persists and survives restarts. Surface: `POST /cron {…, guard}`, CLI `con cron add … --guard "<cmd>"` or `--guard-file <path>`. **`--guard-file` INLINES the file's contents into the cron record** (the path is not referenced), so later edits to the script don't propagate — remove + re-add the task, or use `--guard "bash ~/exec/x.sh"` when you want the file to stay live. `runOnce`/`con cron run` also evaluates the guard (a manual run of a guarded task only wakes if the guard passes).
- **Routes** (`server/src/routes/cron.ts`): `GET /cron[?session=…]`, `POST /cron`, `DELETE /cron/:id`, `POST /cron/:id/run`, `GET /cron/upcoming?n=N`, `GET /cron/ics-token` (returns `{token, publicUrl}`), `GET /cron.ics?token=…` (constant-time compare; 403 on bad token; `Cache-Control: max-age=300`).
- **ICS**: `server/src/cron/ics.ts` expands each task into discrete VEVENTs (next 50 firings, 30-day window) via `Croner.nextRun()` — avoids the lossy cron→RRULE conversion. UTC timestamps, RFC5545 line folding + escaping. Calendar clients re-fetch periodically.
- **CLI**: `con cron list/add/remove/run/upcoming/ics-url`. `--trigger` accepts a 5-field cron, ISO datetime, or `+30m`/`+2h`/`+1d` (CLI resolves relative to ISO). `--once` flips recurring=false (implied for ISO/relative).

### Pebble Index 01 ring (`con ring`) — webhook archive + voice-command tree (^kind-bee)
A smart ring with one button + a mic (Core Devices; single click-hold = the ring's own note agent, double click-hold = configurable). Its app can POST every recording to ONE webhook **in addition to** its own agent run, and **never shows the HTTP response** — so Console's feedback is a push notification, never the reply body. Docs: `https://help.repebble.com/en/articles/15724406-index-advanced-features-mcp-webhook`. Yousef's intent (blog post 2026-09-02): a `con`-like tree of short commands, spoken to **projects and lists, not agents** — `log dream …`, `add movies …`, `add console …`, `message mum …` — AL as the final fallback. **There is deliberately NO `agent <name>` verb** (an early version had one plus name-first addressing; Yousef: "Why did you make an agent command? Did you not read what I wrote?") — `add <project> …` files a card and the board forks the agent; AL is reached only as the unclaimed-text fallback.
- **Wire shape** (live-verified against curl's multipart + a real ring test event, 2026-09-02): `POST https://con.amar.io/hub/ring/webhook`, `multipart/form-data` with parts `audio` (`audio/mp4`, M4A, ≤~2 min), `transcription` (text — ABSENT when the ring's STT failed, so it must be optional), `recordedAt` (ms epoch), `client` (`ring`); header `X-Audio-Size` when audio present, plus user-defined headers. Auth = the normal wall: `con ring setup` mints a **`ring`-scoped bearer** (`HubTokenScope`) and prints the URL + `Authorization: Bearer …` to paste into the Pebble app. Nothing under `/ring/*` is exempt. `POST /ring/webhook` also accepts JSON `{transcription|text}` — that's `con ring say "<text>"`, the schema dev loop.
- **Hub** `server/src/ring/`: `multipart.ts` (pure Buffer-walking parser + `buildMultipart` — NOT the `toString('binary').split()` hack `/stt` uses), `store.ts` (`RingStore` → `~/.config/console/ring/recordings/<id>.m4a` + `<id>.json` sidecar; ids sort chronologically; **append-only, no delete/prune API** — posterity), `schema.ts` (the tree as DATA — see below), `schema-loader.ts` (hot-reload from the vault, last-good on a broken edit), `router.ts` (PURE rules), `append.ts` (pure note edits: dated log bullet / list bullet / movie table row), `llm-fallback.ts` (`claude -p` on `smallFastModel()`: the classifier + the movie enricher; strict JSON, off-schema → null), `pipeline.ts` (`processDelivery`: archive → transcript → route → execute → notify; every hub touchpoint via `RingCtx` so it's stub-testable — `server/src/__tests__/ring.test.ts`). Routes `server/src/routes/ring.ts`: `/ring/{webhook,status,schema,recordings[?limit],recordings/:id,recordings/:id/audio}`; ctx wired in `index.ts` beside `configDir` (must sit AFTER `configDir` — TDZ). CLI `con ring {status,setup,list,show,audio,say,schema}`.
- **The command tree lives in a vault note, `projects/console/ring-schema.md`** (Yousef's "visibility over the command tree" ask, 2026-09-02). Handlers are code (a new *kind* of action is code anyway); the note's ```yaml fence owns the PHRASING: `fallback`/`llm_fallback`, and per verb `aliases` + targets — `log.targets` (name → file), `add.targets` (name → file or `{file, enrich: movie}`), `add.project_column`, `message.contacts` (nickname → `users/<name>.md`). `RingSchemaLoader` re-reads it on every delivery (tiny file), **seeds it from `seedSchemaNote()` when missing, and keeps the LAST GOOD schema when the yaml is unparseable** — a mid-edit typo must not flip routing to defaults. `con ring schema` prints the effective tree with every target resolved (file exists / project known / contact in AL's workspace / agent live); `--check` exits 1 on parse errors or unresolved targets. Parse errors also ride `GET /ring/status.schemaErrors`.
- **Transcript precedence**: ring's `transcription` → else hub batch STT on the audio (`al/transcribe.ts` `transcribeAudio`, `audio/mp4`) → else archived with a "no transcript" push and no routing. Sidecar records `transcriptionSource: 'ring'|'hub-stt'|null`.
- **Routing — deterministic first, LLM last, by Yousef's design.** `normaliseKeepCase()` (NFKC, curly quotes, leading fillers `hey/ok/um/please…`, trailing punctuation) — matching runs on its lowercase form, **payloads keep the speaker's case** (a dream log shouldn't read all-lowercase). Shape `<verb> <target> <payload>`: the first word resolves to a verb by name, schema alias, or ONE edit (`fuzzyEqual`: words ≥4 letters only; `pickFuzzy` never guesses between two candidates), the second word to a target the same way, the rest is payload. Rules (`rule` recorded in the sidecar): `log` → dated bullet (`## YYYY-MM-DD` + `- HH:MM text`); `add.list` → bullet, or the `movie` enricher's table row (`| Title | Year | Series | No |`, padded to the header, falls back to a bullet when the LLM can't identify it); `add.card` → `BoardOps.add` on the project board (`project_column`, default Backlog — a project slug as the target; hyphenated two-word slugs like `reflection tools` work); `message` → **relayed THROUGH AL** with attribution (`buildRelayEnvelope` — the WhatsApp number is AL's identity, so the hub never sends Yousef's words as AL's own; `tell`/`text`/`whatsapp` are default aliases); music transport = whole-utterance rules (`play|pause|next|previous`, `play <query>` → top Spotify track), checked BEFORE the verb tree so a bare `play` isn't a verb with a missing target. **A matched verb with an unknown target is `unknown-target`**: a "no log target called X — add it to the schema note" push, never a fallback to AL (mis-hearing a target shouldn't hand a garbled command to an agent). Only when NO verb fires: `llm_fallback` → `classifyWithLlm` (may only pick targets from the schema/env; off-schema → no match) → `fallback` agent (AL by default, delivered with a `[RING — voice command …]` envelope — the ring's own agent already handled any plain note, so anything reaching us via the Console-only trigger is meant as a command) → `unknown`. `route.via` (`rule|llm|default|none`) + `rule` land in the sidecar so the tree can be tuned from `con ring list`.
- **Execution feedback**: result → `pushServer.broadcast` (`type:'agent', pane:'agents'` when a session was addressed, else `generic`; id `ring:<recId>`). A dead target is reported ("X is not live"), never silently swallowed. Latency: rules are µs; hub STT 1–3 s only when the ring sent no transcript; the LLM classifier ~10–15 s only on a rule miss (`llm_fallback: false` skips it).
- **Recommended ring config**: Send = both, Trigger = the button combo reserved for Console (double click-hold) so plain notes never hit the fallback agent. Not built: an MCP-sandbox server (the ring's cloud agent calling Console tools — Yousef wants string parsing, so the webhook is the primary path); SPA/APK surfaces for the archive (`con ring list/show/audio` is the current reader).

### Push-to-talk (PTT) — system-wide hold-to-talk → STT → mic owner
A hardware/hotkey hold-to-talk that streams mic → hub `/stt` (OpenAI realtime, `{type:'audio',data:b64}` → `{interim|final,text}`) and on release routes the transcript to the **mic owner** session. Owner model in `server/src/mic.ts` (`MicState`: `ownerSessionId` persisted to `mic-owner.json`, transient `hot`); routes in `server/src/routes/mic.ts` (`/mic/status|owner|hot|say|compose`); SyncBus `mic` service in `index.ts` broadcasts `state` (owner/hot) + `compose` (transient, NOT in the subscribe snapshot — and the SyncBus never replays missed events). Default owner = explicit-if-live-else-Al. CLI `con mic status|give|pass|release|say|ptt`. SPA mirror in `src/store/mic.ts` + the `MicButton` in `AgentTab`.
- **Two delivery modes**: `/mic/say` = inject + **auto-send** to the owner; `/mic/compose` = drop into the owner's composer **unsent** for review (`AgentPromptInput` reacts to `composeSeq`). A composed draft **lingers** in the textarea until sent/cleared — by design (it's a review draft), so an earlier foreground compose can still be sitting there later; it is NOT a duplicate of a backgrounded `say`.
- **Desktop** (Sway, out-of-repo dotfiles): `$direct+c`/`$remote+c` hold → `~/exec/con-ptt` → `parec --rate=24000 … --latency-msec=50` → `/stt` WS, live transcript in a `foot` popup (`/tmp/con-ptt.live`), routes to `/mic/compose` (review) on release; waybar `custom/ptt` indicator (`/tmp/con-ptt.hot`).
- **Phone** (APK v26+): the rugged phone's Custom-key **"Open Zello"** Easy-shuttle mode is the ONLY one that emits the firmware-level `com.zello.ptt.down/.up` broadcasts (Zello PTT API action strings — independent of any app). `PushService.pttReceiver` records on `.down` (AudioRecord VOICE_RECOGNITION 24kHz mono PCM16 → `/stt`), and on `.up` routes to `/mic/compose` if `MainActivity.foreground` else `/mic/say`. Needs FGS type `microphone` + RECORD_AUDIO. The native service requires the **apk bearer** (pair the APK) — see [Known Issues] + `memory/project_android_js_bridge_bind.md`.
- **Two STT models, deliberately NOT one constant** (`server/src/stt.ts`). The realtime endpoint (`wss://…/v1/realtime?intent=transcription`) and the batch endpoint (`POST /v1/audio/transcriptions`) reject each other's model ids, so they need separate constants — `STT_MODEL = 'gpt-realtime-whisper'` (streaming: PTT, dictation, glasses mic) and `STT_BATCH_MODEL = 'gpt-transcribe'` (whole-file: `/stt` upload endpoint + Al's WhatsApp voice notes). A test in `__tests__/stt.test.ts` pins `STT_BATCH_MODEL !== STT_MODEL` so a "consolidate these" refactor fails loudly. **`gpt-live-transcribe` was live-A/B-tested (2026-07-31) and REJECTED** — it connects and accepts the identical GA session config but transcribes measurably *worse* than `gpt-realtime-whisper`; adding `turn_detection: server_vad` for it then breaks the explicit `input_audio_buffer.commit` (`input_audio_buffer_commit_empty` — VAD already consumed the buffer). **When probing the realtime endpoint, stream at true realtime pace (4800-byte chunks / 100 ms at 24 kHz mono PCM16)** — faster starves the streaming decoder and garbles every model, invalidating the comparison.
- **A turn only ends because the CLIENT says so — `{type:'done'}` on mic release** (`server/src/index.ts` `/stt` handler; `STT_FLUSH_IDLE_MS` / `STT_DONE_TIMEOUT_MS` in `stt.ts`; fixed 2026-08-11 after "no text at all off mobile"). `gpt-realtime-whisper` **rejects `turn_detection`**, so nothing closes a turn on its own: it streams deltas lazily and the tail sits unemitted for 5–8 s. Every client used to close the socket the instant the mic was released, so the ending was discarded — short utterances lost their last words and brief ones produced **nothing at all**. (The relay *had* a `let commitInterval` declared with a "periodically commit" comment that was **never assigned** — so no commit was ever sent. Dead code that read as a working feature.) Two commit triggers now exist, and **neither is a wall-clock timer** — that distinction is load-bearing, since periodic commits chop mid-sentence and were vetoed for wrecking accuracy (`memory/feedback_stt_no_periodic_commits.md`): (1) **idle** — every `append` resets a `STT_FLUSH_IDLE_MS`=600 ms timer, so a commit only lands in a genuine gap; (2) **`{type:'done'}`** — commits immediately, then the relay holds the socket open until the `final` lands and **closes it itself** (capped by `STT_DONE_TIMEOUT_MS`=4 s so a stuck turn can't strand the mic UI). Measured commit→`final` ≈ 600–700 ms, which is why the old flat 600/700 ms client grace periods were racing it and losing.
  - **The START of the turn is guarded too (fixed 2026-08-21): no audio is dropped during either handshake.** Two independent losses made the first words of a dictation vanish for anyone who talks the moment they hit the mic: (1) the hub relay silently discarded frames arriving while the OpenAI WS was still CONNECTING (~0.5–1.5 s TLS+WS) — it now buffers them (`pushCapped` in `stt.ts`, oldest-evicted at `STT_PREBUFFER_MAX_BYTES` ≈ 30 s) and flushes on open, with a `done`-during-handshake committing right after the flush; (2) `useDictation` serialized getUserMedia → WS open → only then built the capture graph, so the browser wasn't even recording until the client WS opened — capture now starts immediately with its own pre-open frame queue, and the WS + getUserMedia open concurrently. Same pre-open queue added to `~/exec/con-ptt-stream.mjs` (its `rec.stdout` handler used to attach only on open). The two Kotlin paths need nothing: OkHttp queues `send()` before the connection opens, so they always captured from t=0 — their loss was (1), fixed hub-side for all four clients at once. Also: a browser whose SpeechRecognition fails with `network`/`service-not-allowed` (Brave) burns seconds discovering it per dictation — `console:dictation:hubOnly` localStorage remembers the failure and goes straight to hub STT forever after.
  - **Four independent implementations, all of which must send `done` and wait** — a fix to one is a fix to none of the others: `src/hooks/useDictation.ts` (SPA + APK WebView), `android/.../core/Dictation.kt` (native composer mic), `android/.../PushService.kt` `pttUp()` (hardware PTT key), and the out-of-repo `~/exec/con-ptt-stream.mjs` (Sway desktop PTT — easiest to forget).
  - **The `final` carries the WHOLE turn, so it supersedes the accumulated deltas** — appending it duplicates the utterance. The two Kotlin paths and the desktop script now replace rather than append; the SPA instead *suppresses* the final when deltas already covered it (`sawDeltaRef`), and that flag must **not** be reset in the teardown path — the final arrives *after* `stop()`.
- **`android/zello-shim/`** — a tiny invisible stub app with applicationId **`com.loudtalks`** (Zello's REAL package — `com.zello` is only the broadcast prefix). "Open Zello" deep-links to the Play Store when `com.loudtalks` is absent; installing this no-op (a translucent activity that finishes instantly) makes the firmware's launch resolve to nothing visible while the PTT broadcasts keep firing. Build `./gradlew :zello-shim:assembleDebug`, served at `/public/apk/loudtalks-shim.apk`.

### Android APK

The local `roomState` cache (name, avatar mxc, members with displayname+avatar) + `directRooms` set (from global `m.direct` account_data) are still maintained per sync tick + from the `snapshot` RPC, and still source per-event `senderName`/`senderAvatarMxc` from `members`; they're just the fallback for name/isDirect/avatar now.

## Hub Routes
External clients reach all of these under `${origin}/hub/<path>` via Caddy (the prefix is stripped before the upstream sees it). Local-host clients (CLI, Al) hit `https://127.0.0.1:9877/<path>` directly with a bearer. The `/public/*` and `/auth/google/*` paths are the only ones the auth middleware lets through unauthenticated.
- `/auth/*` — Google + Monzo + Matrix OAuth flows.
  - `/auth/session` (GET) + `/auth/session/logout` (POST) — current hub session (cookie-derived).
  - `/auth/hub/sessions` (GET) — list active browser sessions (id-prefixes only).
  - `/auth/hub/tokens` (GET/POST), `/auth/hub/tokens/:id` (DELETE) — name + scope-keyed bearer tokens for non-browser clients. POST returns the plaintext once.
  - `/auth/hub/allowed-emails` (GET/POST), `/auth/hub/allowed-emails/:email` (DELETE) — Google allow-list. Default: `['yousefamar@gmail.com']`.
- `/mail/*`, `/cal/*`, `/matrix/*`, `/money/*`, `/bookmarks/*`, `/feeds/*`, `/notes/*` — service proxies / CRUD. `POST /notes/open` is the odd one out: a UI remote-control relay, 409 when no SPA client is subscribed (see Notes → Remote-open).
- `/owntracks/*` — proxy to the self-hosted OwnTracks Recorder (`maps.amar.io`, basic auth injected), plus `GET /owntracks/status` (configured-ness, never the password) and `POST /owntracks/credentials` (`{url?,username?,password?}`, merged). `/geocaching/*` — gc.com scraper (status/credentials/fetch-area/caches/cache). (Map basemap is on-demand OpenFreeMap vector tiles loaded directly by the client — no hub route.)
- `/debug/*` — debug agent log, eval, state, screenshot, toggle. `/debug/eval` is loopback-only (Phase 9+).
- `/push` (WebSocket), `POST /push/send`, `GET /push/status` — push notification channel consumed by the APK's PushService. Carries glasses WS RPC framing (see Glasses section). PushService attaches `Authorization: Bearer <apk-scoped-token>`.
- `/glasses/*` — low-level dumb pipe proxied to the APK's GlassesService over the `/push` WS.
- `/dashboard/snapshot`, `/dashboard/alerts`, `/dashboard/servers`, `/dashboard/costs` — Home pane data sources.
- `/dashboard/canvas/{islands,tabs}` — CRUD + per-slug `POST/GET/DELETE /publish` for the public-token surface.
- `/canvas/*` — static file serve from `~/.config/console/canvas/` (the AI agent canvas dir). `DELETE /canvas` wipes + re-seeds the placeholder. fs.watch broadcasts `dashboard.canvas_changed` on the SyncBus.
- `/public/*` — unauthenticated surface. Three things live here:
  - `/public/<slug>/` — published tab/island standalone page (short form, tab-first-then-island; explicit `/public/canvas/<tab|island>/<slug>/` disambiguates a dual-published slug; NO token — publish = the slug URL is public); `/<slug>/<asset>` serves tab assets (`path.resolve` guard). Published slugs persist at `~/.config/console/canvas-public.json` (sibling of `canvas/`, survives `con dashboard canvas reset`).
  - `/public/cron.ics?token=…` — Google Calendar subscription; the cron token in the query is its own auth. Legacy `/cron.ics` is Caddy-rewritten to this.
  - `/public/apk/latest.json` + `/public/apk/console-<n>.apk` — APK update channel. Legacy `/apk/*` is Caddy-rewritten to this (so pre-v20 stuck installs can still pull v20+).

### Inbound flow
Baileys `onMessage` (after `fromMe` filter) → `ensureUserKnown` → `inboundEnvelope(msg, resolvedUser)` → `injectToAl(envelope, broadcast)`. The envelope is **task-framed** (not a chat message) so Claude doesn't default to a silent in-session reply. Shape:
```
[INBOUND WhatsApp — action required]
From: <senderName> (<sender-jid>) — resolved user: <name or "unknown">
Thread: <jid>
Message ID: <wamid.HBgL...>

Message:
<body>

[Attached image(s) (Read these paths): /tmp/console-al-inbound/<id>-0.jpg]   ← only when an image is attached
[INBOUND WhatsApp] Attached file (audio, audio/ogg): /tmp/console-al-inbound/<id>-0.ogg   ← audio/video/document, any type
Voice note transcript: "..."   ← only for a ptt voice note (OpenAI preferred, Gemini fallback via GEMINI_API_KEY)

---
ACTION ... con whatsapp send <jid> --body "..."  (a session-only text reply is invisible to the sender)
```
Inbound images/audio/video/documents are all downloaded by `whatsapp.ts` (any Baileys media type, not just images — generalized 2026-07-31), written to `os.tmpdir()/console-al-inbound/` (documents keep their real filename), and their paths injected into the envelope so Al can `Read` them (the text-only inject path can't carry bytes). Voice notes (audio + `ptt`) are additionally auto-transcribed via `al/transcribe.ts` and the transcript is inlined in the envelope — no OPENAI_API_KEY/GEMINI_API_KEY configured just skips transcription (never blocks delivery of the audio file itself). Voice delegate envelopes use a `[Voice delegate from ...]` header with explicit "reply will be spoken aloud" guidance.

### Conversation forks (per-thread routing, 2026-08-24 — `al/conversation-forks.ts`)
**Non-owner WhatsApp threads no longer inject into Al's main session.** `routeInbound()` (wired in the `onInbound` handler before `injectToAl`) forks AL per thread JID (`AL ↔ <person>`, `--fork-session` off Al's claudeSessionId) and routes all later messages from that thread to the fork; **Yousef's threads always go to the parent** (`resolvedUser === 'yousef'` bypass — routing the owner through a digest-delayed fork would hollow out parent-Al). Why: privacy (concurrent conversations — e.g. Mai + Nica — never share a context window, so per-contact deny-walls become a physical boundary) + parent context hygiene. Mechanics: routing table persisted at `~/.config/console/al-conversation-forks.json` (atomic write; restored on boot by `startConversationForks`, which re-points hub ids the restore loop re-minted via claudeSessionId match and drops dead records); messages arriving during the fork's spawn gap queue in `pendingSpawns` and flush on `session_init` (the `--fork-session` no-init-until-first-input gotcha applies — seed + first envelope are sent immediately); fork spawn failure falls back to the parent (never drops a message). **Idle wind-down** (1 min sweep, 1 h idle): substantive conversations (>2 inbound msgs or marked substantive) digest-merge into the parent via `mergeIntoParent`; trivial ones reap silently (transcript survives on disk + chat archive — a digest of "thanks/np" isn't worth 2 turns); a mid-turn fork gets its deadline pushed, never interrupted. Unit-tested in `__tests__/conversation-forks.test.ts` (stubbed createSession/wakeSession/merge; forks file via `CONSOLE_AL_FORKS_FILE`).
- **A contact is one PERSON across two JIDs, and the thread alone can't show what they're replying to (^rosy-kiwi, 2026-09-02).** Al's sends go to whichever JID he picks (usually the phone `447…@s.whatsapp.net`); the reply often arrives from the linked-device `…@lid`. The Al↔nica fork answered "Thank youuu" with a 34-hour-old yoga message instead of the dinosaur fact sent 60 s earlier: the ring sends said "Veronica" → phone JID, the inbound said "Nica" → lid, and the seed's "ONE conversation (thread …@lid)" framing made the model treat them as separate threads. Fix = label the IDENTITY at both ends, never restate history (a first version quoted Al's last 3 sends into every envelope — Yousef vetoed it as heavy/redundant; the model already has the transcript, it just didn't know the two names were one person): (1) the envelope's From line reads `resolved user: nica (same person as 447776912442)` (`identifiersFor(user)` minus the sender's own id, via `users.ts`); (2) `POST /whatsapp/send` returns `user: <resolved>` beside `jid`, so the send's tool result in the transcript carries the same canonical name the inbound will; (3) `forkSeed` names the other identifiers as "the SAME PERSON". ~10 tokens per event. Tests in `__tests__/al-contact-identity.test.ts`.

### Read-only session peek (`con agent peek`, `GET /agents/peek`)

## Known Issues
- Matrix E2EE: new device needs key backup restore (`POST /matrix/keys/restore-from-recovery-key`) before old messages decrypt
- Matrix E2EE: hub device must be cross-signed or Beeper bridges silently drop encrypted messages with `com.beeper.undecryptable_event`. Run `POST /matrix/keys/restore-cross-signing` after a hub re-login.
- `bootstrapCrossSigning(true)` overwrites server keys — always restore keys FIRST (the route above uses `reset:false`)
- WASM `UserId` objects consumed per call — create fresh instances each time

## Matrix recovery workflow (hub-side)
The old browser "Settings → recovery key" flow was dropped in the hub-centric migration. Hub-side replacements live in `server/src/matrix/backup-restore.ts` + `secret-storage.ts`, exposed as:
- `POST /matrix/keys/restore-from-recovery-key {recoveryKey}` — decodes an `EsU…` key; tries direct `BackupDecryptionKey` match first, then SSSS unlock. SSSS path iterates **every** keyId that encrypts `m.megolm_backup.v1` — users often have the current default SSSS key point somewhere new (e.g. `RII4BrO2Ox`) while the backup secret is still encrypted under the previous key (e.g. `bXFaNVGpGwtYSl7WxkfM2aznevIvcl3z`). Decrypts all sessions via `/room_keys/keys` and imports into OlmMachine (+ persists via `saveBackupDecryptionKey`).
- `POST /matrix/keys/restore-cross-signing {recoveryKey}` — decrypts the three cross-signing private secrets (`m.cross_signing.{master,self_signing,user_signing}`) from account_data, calls `importCrossSigningKeys` then `bootstrapCrossSigning(false)`, and explicitly sends the returned device-signature upload (bootstrap requests do NOT flow through `outgoingRequests()`). Required after any hub re-login — bridges reject Olm from uncross-signed devices. Beeper's current default SSSS key `RII4BrO2Ox` ships with **no `iv`/`mac` verification block**, so the helper skips `verifySsssKey` when those are absent and relies on the secret's own MAC to reject wrong keys.
- `POST /matrix/keys/import-local-backup` — force-imports the on-disk M0 key backup into the hub's current OlmMachine. Useful after hub migrates to a new deviceId and the legacy browser-exported keys never got merged.
- `POST /matrix/decrypt-event {roomId, eventId|event}` — fetches raw event from the homeserver (or takes it inline) and decrypts via the hub's OlmMachine. Used to resurrect "🔒 Encrypted message" placeholders that the browser persisted to IDB when the hub couldn't decrypt them at sync time.

**"🔒 Encrypted message" placeholders in one room = a withheld Megolm session**, usually because the hub device wasn't cross-signed when the bridge shared keys (each hub re-login re-opens this hole; `withheld_sessions` in `matrix-crypto-snapshot.json` lists the gaps, ~19 rooms seen 2026-08). Recovery that works: have the phone (Beeper Android) toggle key backup so the session uploads (`GET /room_keys/keys/<roomId>?version=N` to confirm), then run the recovery-key restore — **no user-supplied key needed**: the hub's own stored seed at `matrix-crypto-snapshot.json` → `stores.backup_keys.recovery_key_v1` (base64-of-JSON-byte-array) re-encodes as `0x8b 0x01 + seed + parity` in base58 into a valid `EsU…` key. Direct `m.room_key_request` to-device sends are never answered (Beeper's rust-sdk clients don't forward keys); backup is the only reliable route. Stale placeholder rows in browser IDB self-heal on re-pagination (bulkPut on event_id).

Multiple rotations of the recovery key are fine — keep older keys handy because `tryKeyAgainstVersion` walks **all** backup versions and the SSSS loop walks **all** keyIds, so any historical key that unlocks any of them still restores. Beeper's recovery keys (`EsU…` prefix) are SSSS keys, not direct `BackupDecryptionKey` seeds. Cross-signing secrets are often encrypted under a **different** (newer) SSSS key than megolm backup — the two routes accept different recovery keys on the same account.
